### US-1 登入後瀏覽會議室並完成單次預約（優先級：P1）

#### Scenario: S-1-1 登入後建立合法預約並確認

```gherkin
Scenario: 登入後建立合法預約並確認
  Given 員工持有有效帳密且有一間啟用中的空閒會議室
  And 目標時段無已確認預約亦無維護時段
  When 員工登入並送出用途、人數、設備需求與合法時段皆齊備的預約
  Then 系統建立一筆屬於該員工的已確認預約
```

**對應欄位**:

- **US**
  - US-1 登入後瀏覽會議室並完成單次預約（優先級：P1）
- **AC / Edge**
  - AC-1-1 登入後合法預約應建立為已確認
- **FR**
  - US1-FR1 帳號密碼登入並辨識角色
  - US1-FR3～US1-FR4 接受完整單次預約並留下已確認紀錄
- **API**
  - `POST /api/auth/login` 建立登入會話
  - `GET /api/rooms` 取得可預約會議室
  - `POST /api/bookings` 建立已確認預約
- **Data**
  - data-plan：Booking 必填用途、人數、設備需求、起迄與預約者，新建狀態為 `confirmed`
  - DDL：預約保留使用者與會議室關聯，且起迄順序有效

```gherkin

```

**對應欄位**:

- **FR**

- **API**
  - `POST /api/bookings` 以預約衝突結果拒絕重疊時段
- **Data**
  - data-plan：只有 `confirmed` 預約占用時段，採半開區間判斷重疊
  - DDL：`bookings_confirmed_no_overlap` 排除同室已確認時段重疊

- Gherkin 僅使用登入、會議室、預約、取消、停用與維護時段等領域語言；API 路徑、頁面與持久化細節只放在對應欄位。
- 後端 Scenario 證明 API 回應與必要持久化結果；前端 Scenario 可用可控資料或 Mock 證明畫面；整合 Scenario 必須以真實前後端 REST 串接。
- 同一 AC／Edge 前後端皆可觀測時使用同一業務 Scenario ID 寫入兩區；併發重疊的純前端 Mock 無法證明資料不超賣，因此 Edge-G-1 前端欄為 `—`。

- 所有業務日曆與對外時間語意以 `Asia/Taipei` 解讀；瞬間持久化與傳輸遵循上游資料與 API 計畫。
