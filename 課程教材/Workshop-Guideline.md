# 第一部分：為什麼 AI 讓你寫得更快，卻更不敢 merge？

## 1.1 五個痛，你中了幾個

- 前兩週飛快，第三週改不動。AI 產出速度遠大於人 review 速度，沒被看過的部分就變成技術債，而且是利滾利。
- 同一個需求，換一個對話問，答案不一樣。因為你的規格活在聊天記錄裡，關掉視窗就沒了。
- 你叫它改 A，它順手改壞 B。因為 AI 沒有你腦袋裡的隱性邊界，它只知道你這一句 prompt 說了什麼。
- 沒有測試保護，所以不敢重構。每次改動都是賭。
- 交接時，理解落差沒有任何東西接得住。PM 想的、SA 分析的、RD 實作的，差異落在會議、Slack、口頭。

## 1.2 五個痛的同一個根因

- AI 的輸入是模糊的自然語言加上你腦袋裡的隱性 context，輸出卻是精確的程式碼。
- 中間那段推理，沒有留下任何可以被檢查、被追溯、被重跑的東西。
- 所以問題從來不是「AI 會不會寫 code」。AI 早就會寫。問題是中間那段推理，你檢查不到。

## 1.3 SDD 是什麼

- SDD（Specification-Driven Development，規格驅動開發）：把「需求到程式碼」中間那段推理，顯性化成一連串可檢查的產物（Artifact）。
- 規格是單一真相來源，進 repo、進版控，跟 code 一起活，不是躺在聊天記錄裡。
- 每一步的輸入是上一步的產物。中間任何一份不對，下一步就會歪，而且看得出歪在哪。
- 人審的是產物，不是 code。審一份 200 行的 API 合約，比審 5000 行的實作便宜太多。

## 1.4 Artifact-First 的順序

- 不是「先寫規格再寫 code」這麼淺。是每一個開發階段，先定義出那一階段該產出什麼形狀的產物，再回頭設計「怎麼產出它」。
- 第一問：這一步結束時，桌上應該多出一份什麼東西？（Artifact）
- 第二問：這份東西長什麼樣才算合格？（Template 與檢查點）
- 第三問：AI 要怎麼被引導才能產出它？（Skill 的 SOP 與 Rules）
- 順序反過來就是 vibe coding：先丟 prompt，再看它生什麼，然後接受它生的東西。

## 1.5 傳統 SDLC 與 SDD 的完整對應

- 需求訪談與需求分析，對應 `/specify` 加 `/clarify`，產出 `spec-mapping-checklist.md` 與 `spec.md`。
- 系統分析與系統設計，對應 `/system-analyze`，產出 `technical-research.md`、`plan.md`、`data-plan.md`、`DDL.md`、`api-plan.md`、`ui-plan.md`。
- 測試計畫，對應 `/e2e-test-plan`，產出 `e2e-test-plan.md`。
- 實作計畫與排程，對應 `/task-plan`，產出三份 `task-*.md`。
- 品保與文件審查，對應 `/analyze`，產出 `analyze-report.md`。
- 實作與測試，對應 `/implement`，內含 TDD Red-Green-Refactor，產出程式碼與測試。

三件事要記住：

- 推理順序沒有變。SDD 沒有發明新的軟工，它只是把同一套推理交給 AI 執行，並且把產物從「給人看的文件」變成「給下一步吃的輸入」。
- 傳統 SA 文件寫完常常就過期，因為沒人真的拿它去做下一步；`api-plan.md` 過期會立刻出事，因為 `/e2e-test-plan` 讀的就是它。
- 傳統是每個階段換一個人（PM → SA → RD → QA），交接處就是落差發生的地方；SDD 是每個階段換一個 skill，人的位置從產出者移到審查者與拍板者。

## 1.6 為什麼拿 SpecKit 當實踐範例

- 大部分講 SDD 的內容，停在「先寫規格再寫 code」這個口號層。
- 落地要回答的是這六題：規格要有哪幾份？每一份格式長什麼樣？誰產誰審審什麼？上一份改了下游怎麼跟？兩份矛盾誰來抓？怎麼套進我們公司的架構與規範？
- 這六題答不出來，SDD 就只是一句正確的廢話。
- SpecKit 是目前把 SDD 流程固化成可執行指令、落地做得相對完整的開源工具，所以我們拿它當範例。
- 但今天用的是改良版，改了四件事：系統分析拆成三份介面合約、加了測試計畫這一層、實作接上 TDD、Skills 模組化成 SOP／Rules／Templates／Scripts。

## 1.7 全貌：12 步流程

```
[1-3 規格]        clarify → mapping-checklist → spec.md
      ↓
[4-5 研究]        technical-research.md + plan.md
      ↓
   === 閘門 1：人 Review，回「繼續」才往下 ===
      ↓
[6-8 介面合約]    data-plan + DDL / api-plan / ui-plan
      ↓
[9 測試計畫]      e2e-test-plan.md
      ↓
[10 實作計畫]     task-backend / frontend / integration
      ↓
[11 一致性]       analyze-report.md
      ↓
   === 閘門 2：有嚴重項就硬停，選先修或繼續 ===
      ↓
[12 實作]         TDD Red → Green → Refactor → 程式碼
```

- 5+2 的意思：5 是主鏈 `/specify` → `/system-analyze` → `/e2e-test-plan` → `/task-plan` → `/implement`；+2 是兩個橫向 skill `/clarify` 與 `/analyze`，隨時可以插入。
- 12 步是把主鏈展開到「一份產物一步」的顆粒度。
- 課綱上寫的 4+2 是不含 TDD 的純 SDD 主鏈，今天實操把實作接上 TDD，所以會看到 5+2。

接下來你會把這 12 步從第 1 步跑到第 12 步，每一步跑完都會打開產物逐行看。

專案裡什麼都沒有，資料表、API、測試、程式碼，全部是你自己產出來的。

# 第二部分：AI × 需求初步撰寫

## 2.1 先自己想一遍

1. 先不要動 Agent。把 2.2 那段需求整段讀一遍。
2. （不要用 AI）讀完之後，拿紙筆或開一個空白檔，自己列出你認為這段需求裡有幾條「還沒拍板的爭議」。
3. 列完先放著，等一下要跟 AI 問你的題目對答案。

## 2.2 貼上需求

1. 在 Agent 開一個全新的對話，不要接在舊對話後面。
2. 把下面整段複製，貼進對話送出。

   ```text
   /specify

   package: 001-meeting-room-booking

   需求：
   我們公司要做一個內部共享會議室預約系統，前後端都要有，本機就能跑。

   平常員工要能瀏覽各樓層會議室（名稱、樓層、容納人數、有沒有投影機／視訊設備），選日期時間後送出預約。預約要寫用途、預期人數、需要哪些設備。同一個會議室不能被兩個已確認的預約佔用同一時段——這是鐵則。但如果有人送出的時段撞到別人，系統要怎麼處理我們還沒吵完：有人說直接擋下並提示衝突；有人說可以進候補清單，前面取消了就自動遞補；還有人說超過 8 人的會議室一律要部門主管審核才能確認。

   管理員要能設定會議室維護時段（黑名單時段），那段時間任何人都不能預約。也要能新增／停用會議室。停用後既有預約怎麼辦？有人說強制取消並通知，有人說只擋新預約、舊的照常。

   員工要能看「我的預約」、取消自己的預約。主管要有一個審核佇列，通過或駁回，駁回要填原因。取消後若有候補，要不要自動升成確認？這點也還沒定。

   我們希望有日曆視圖跟列表視圖兩種看預約的方式。首頁最好能一眼看到今天各會議室忙不忙。另外有人提到要支援每週重複預約（例如每週三 14:00–16:00 開站會），但另一派人覺得第一版不要做重複，太複雜。還有人說要做「邀請與會者」，被邀請的人要能回覆參加／不參加——但也有人說第一版只要記人數就好，不要個人邀請。

   技術上前端 Vite，基本上會採用 Bootstrap5 元件開發，後端使用 Express、前後端只走 REST、DB 用 PostgreSQL。有人想塞 Redis 做鎖防超賣，有人覺得本機 SQLite／Postgres 交易就夠。通知要用 email，但本機開發環境又沒有真的 mail server——要不要先做站內通知就好也沒定。

   權限大致分三種：一般員工、部門主管、設施管理員。登入方式有人說先做簡單帳密就好，有人說要接公司 SSO；第一版先用什麼還沒拍板。時區一律台北，營業可預約時段預設平日 09:00–21:00，但假日能不能預約也沒共識。預約最短 30 分鐘、最長 4 小時，這個比較確定；但「能否跨日」沒人講清楚。

   最後：同一個人對同一會議室同一天最多幾筆預約？有人說不限，有人說最多 2 筆以免霸佔。報表／使用率統計有人想做，但可以排後面。

   須遵守專案憲法技術基線。
   ```

3. 觀察一下結果。它不會直接寫規格，會先停下來訪談你，這一步叫 `/clarify`。

## 2.3 觀察它問你的問題

1. 對照 2.1 你自己列的清單，回答底下問題：
     - a. 它一次問了幾題？
     - b. 它問的這幾題，跟你自己列的重疊了幾條？
     - c. 你列了但它沒問的那些，你覺得為什麼它不問？
2. 觀察每一題的組成，它是這樣排的：
     - a. Context — 先給你足以判斷的背景，而不是丟一個光禿禿的問題。
     - b. 總結之提問 — 一句話講清楚要你決定什麼。
     - c. Options — 用表格列出可比較的選項。
     - d. 推薦選項與推薦原因 — 它會表態，但不會替你決定。
     - e. Others — 永遠留一個讓你補充的出口。
3. 這個組成不是隨便長出來的。它就是「AI 只負責發散、把選項攤開，人負責收斂拍板」這件事在流程上的實作。

## 2.4 回答它的問題

1. 回覆格式是 `題號: 選項編號`，一行一題，一次把該輪的題目回完。

   ```text
   1: 1
   2: 1
   3: 1
   ```

2. 想選 Others 的話，先寫 `3: 4`，下一行再補一句說明。
3. 在同一個對話裡回就好，不用另外打 `/clarify`。
4. 選項編號以你當下畫面的 Options 表為準，不是固定 1。
5. 今天的拍板方向照這個回：
     - 時段衝突：直接擋下並提示，不做候補
     - 主管審核：第一版不做
     - 停用會議室：只擋新預約，既有照常
     - 重複預約：第一版不做
     - 與會者邀請：第一版只記人數
     - 登入：簡單帳密，不接 SSO
     - 鎖與快取：不用 Redis，DB 交易即可
     - 通知：先做站內可見
     - 假日預約：不可約
     - 跨日：不可跨日
     - 同人同室同天筆數：不限
     - 報表：第一版不做
6. 如果它又問一輪，重複第 1 步，直到它不再問為止。

   每輪 1 到 3 題，整場最多累計 5 題。上面 12 條你大概只會被問到 3 到 5 條，其餘用不到，這是正常的。沒被問到的爭議會被收進 `spec.md` 的假設章。

7. 想一下：為什麼它只問 5 題，而不是把 12 條都問完？

   認真想過之後，去 `.agents/skills/clarify/rules/盤點高影響需求缺口與提問排序判準.md` 裡面尋找答案。

## 2.5 打開 spec-mapping-checklist.md

1. 打開 `specs/001-meeting-room-booking/spec-mapping-checklist.md`。
2. 觀察一下這份檔案的組成架構：
     - a. 它先把原始需求切成一片一片的「語意片段」。
     - b. 每一片都被標了類型：屬於哪個故事、是全域限制、還是待澄清缺口。
     - c. 倒數第二節是「覆蓋性檢查」，確認原始需求的每一片都有落點；最後一節是「輸出前確認」。
3. 找到「同一個會議室不能被兩個已確認的預約佔用同一時段」這一片，再找到「有人說直接擋下、有人說進候補」那一片。
     - a. 這兩片在原始需求裡是同一段話，為什麼被切成兩片？
     - b. 它們被標成什麼類型？為什麼不一樣？
4. 翻到「覆蓋性檢查」那一節，找找看「報表／使用率統計」這一片跑去哪裡了。
     - a. 它有落點嗎？落在哪？
     - b. 如果一片需求在這裡找不到落點，代表什麼事情發生了？
5. 傳統開發最常見的需求遺漏就是在這一步發生的。差別是這次它被逼著寫下來給你看。

## 2.6 打開 spec.md

1. 打開 `specs/001-meeting-room-booking/spec.md`。
2. 觀察一下這份規格的階層：

   ```
   使用者故事（誰、為了什麼、要做什麼）
     └ FR（這個故事底下必須具備的功能需求）
         └ 成功標準（怎麼算完成，可量測）
             └ 驗收情境 AC ＋ 邊界情境 Edge（Given-When-Then）

   平行一層：共通規則與全域約束（跨故事、永遠成立的才放這裡）
   ```

8. 第 7 步的答案是：NFR 是按「影響範圍」被分配到不同層的。只影響這個 package 的，落在共通規則；跨所有專案的技術基線，落在憲法。NFR 不是寫在一張紙上的一個章節。

## 3.5 三份介面合約產出來了，先搞懂為什麼是三份

1. 它會依序跑資料、API、UI 三個部分。跑完對話會出現收尾總結，下一步指向 `/e2e-test-plan`。
2. 介面就是兩個東西的接觸面。接觸面必須有合約，不然兩邊各做各的就對不起來。
3. 這個系統有三個接觸面：
     - a. 資料 — 程式對資料庫，合約是 `data-plan.md` 加 `DDL.md`，主流標準是 ER 模型與 SQL DDL。
     - b. 服務 — 前端對後端，合約是 `api-plan.md`，主流標準是 REST 加 OpenAPI。
     - c. 呈現 — 使用者對系統，合約是 `ui-plan.md`，標準是頁面、Flow、元件規格。
4. 標準怎麼選？只看三件事：兩邊看不看得懂、能不能被機器驗、團隊現在會不會。
5. 這個專案選 REST 不是因為 REST 比較好，是因為憲法規定前後端只能走 REST。去 `.constitution/core.md` 找到那一條，讀一遍。

   標準是被約束選出來的，不是被喜好選出來的。

6. 底下三小節每打開一份合約，都用這三個問題掃一次：
     - a. 追溯：這裡的每一條，指得回上游的哪一條？
     - b. 完整：上游的每一條，在這裡都找得到落點嗎？
     - c. 一致：三份彼此對得起來嗎？UI 要的欄位 API 有回嗎？API 回的欄位資料表有嗎？

3. 觀察一下這份檔案的階層：

     - a. 它只會落在後端跟前端。後端驗規則本身——打 API，被擋，回衝突狀態碼。前端驗呈現——衝突時畫面要跳提示。

     - c. 落點判準就是這個——不是「重要的就三層都寫」，是「這條非串接不可才進整合」。同一件事三層各驗一次，就是浪費。

     - a. 它寫的是「A 會議室 10:00-11:00 已有已確認預約」，還是「資料庫執行 INSERT INTO bookings」？

     - d. 這種斷點就是第六部分 `/analyze` 要抓的東西——只是這一條在 skill 的規則層，`/analyze` 也抓不到，只有人能看出來。

     - a. 為什麼不隨便寫一條測試假裝有 cover 就好？
     - b. 假裝的那一條，三個月後會發生什麼事？

     - a. 數數看三欄各有幾個勾。
     - b. 你覺得這個比例合理嗎？哪一層應該最多？哪一層應該最少？
6. 現在你學會 30 秒 Review 一份測試計畫了：翻檔尾數三欄的勾看比例，抽三條看追溯欄位回不回得去，看 blocked 每條是不是真的沒拍板。

## 4.5 檢查點

1. `e2e-test-plan.md` 存在，裡面有後端、前端、整合三個區塊。
2. 檔尾有測試摘要總表。
3. 你隨機抽一條 Scenario，能在 `spec.md` 找到它的來源。

# 第五部分：AI × 實作計劃

## 5.1 產出實作計畫

1. 在同一個對話貼上：

   ```text
   /task-plan

   package: 001-meeting-room-booking
   ```

2. 它會產出三份：`task-backend.md`、`task-frontend.md`、`task-integration.md`。上午只看後端那份。

## 5.2 打開 task-backend.md，先看前兩章

1. 打開 `specs/001-meeting-room-booking/task-plan/task-backend.md`。
2. 觀察一下前兩章：
     - a. 第 1 章是「規格閱讀」——列出動手之前要先讀哪些規格。
     - b. 第 2 章是「環境建立」——通常會有五到六個小節，從工具版本、目錄骨架、資料庫服務、套件與腳本、Schema 與連線、一路到測試基建與 smoke。
3. 第 2 章裡一定要找到「起資料庫」那一節，把它讀完。
     - a. 它叫你用什麼方式起 PostgreSQL？
     - b. 服務名、使用者名、資料庫名分別是什麼？記下來，第七部分會用到。
     - c. 如果這一章從頭到尾沒有提到怎麼起資料庫，舉手。那代表上游的技術研究沒把這件事寫進去，第七部分會直接斷。
4. 試著猜測：第 2 章那些要建的目錄，是從哪一份檔案來的？
5. 答案是 3.3 你看過的 `plan.md` 專案結構章。那一章在這裡變成了可執行步驟。
6. 一份合格的實作計畫，是一個新人拿到就能從空資料夾做到完的東西。今天專案裡本來就什麼都沒有，這份計畫就是你的起點。

## 5.3 打開第 3 章，看 TDD 的節奏

1. 往下捲到「3. User Story 實作計劃」，找到 US-1。
2. 觀察 US-1 底下的組成：
     - a. 先是 AC 與 Edge 的清單。
     - b. 然後是 Red 區塊，底下巢狀著「受測行為」。
     - c. 然後是 Green 區塊，底下巢狀著「實作計畫」。
     - d. 最後是 Refactor。
3. 試著猜測並回答：
     - a. Red 底下寫的是「要驗什麼行為」還是「要動哪些檔案」？
     - b. Green 底下寫的又是哪一種？
     - c. 為什麼要把這兩種分開寫？
4. 認真想過之後看答案：Red 寫「送出重疊時段的預約應被拒絕並回傳衝突訊息」，Green 才寫「在某個 service 加入 overlap 檢查、於 repository 層以交易包住」。分開寫，是為了讓 Red 階段不被實作細節污染。
5. TDD 是先寫一個會失敗的測試（Red），再寫最小的實作讓它通過（Green），最後在測試保護下整理程式碼（Refactor）。
6. 它為什麼對 AI 特別關鍵？
     - a. AI 最擅長「讓測試通過」這種有明確終點的任務。
     - b. AI 最不擅長「憑感覺寫一個大功能」。
     - c. TDD 把大任務切成一連串有明確終點的小任務，生錯了錯在一條 Scenario 的範圍內，不是一整包。

## 5.4 練習：判斷什麼是合格的 Red

1. 找到 US-1 的 Red 區塊，看它最後那一個固定步驟——那是「驗紅項」。
2. （不要用 AI）自己判斷底下四種失敗，哪些算合格的 Red，哪些不算：
     - a. 測試跑起來了，打到了建立預約的 API，因為回應是 404 而斷言失敗。
     - b. 測試因為 `ECONNREFUSED` 而失敗。
     - c. 測試因為 import 路徑寫錯而編譯失敗。
     - d. 測試因為斷言的欄位名稱打錯而失敗。
3. 答案：只有 a 是合格的紅。b 是資料庫沒起、c 是程式沒編過、d 是測試自己寫錯——這三種都不是「功能還沒做」。
4. 為什麼要這麼講究？

   如果測試是因為資料庫沒起而紅，你把它當成合格的紅往下走，Green 階段就會寫出一堆對不上的實作，然後你會 debug 兩小時找不到原因。

5. 這個固定驗紅項就是擋這件事的。它把「Red 的品質」變成一格必須勾的 checkbox，不靠自律。

## 5.5 兩種進度：第 3 章的勾選框，跟第 4 章的總覽表

1. 回到第 3 章，看那些 `- [ ]` 勾選框。這才是 `/implement` 真正會動的東西。
2. 試著猜測：`/implement` 會怎麼用這些勾選框？
3. 答案：它從第一個未勾的往下一路做，做完一格勾一格，失敗才停。所以中斷了可以續跑——電腦當機重開，重貼一次 `/implement`，它從第一個未勾的地方接著跑，不會重做已完成的。
4. 再翻到「4. 進度總覽」。它是一張把所有 Scenario 攤平的表，讓你一眼看出這一層總共有幾格要做。
5. 注意兩件事：
     - a. 第 4 章那張表裡的格子不是勾選框，只是符號。
     - b. `/implement` 不會更新它。等一下跑完，第 3 章的勾選框會變、第 4 章的表不會變，那是正常的，不是跑失敗。

     - b. Red 驗的東西一樣嗎？
     - c. 為什麼不一樣？

2. `task-backend.md` 裡每個 User Story 底下都有 Red、Green、Refactor 的勾選框。

它交付完會叫你下一步去跑 `/implement`。先不要。我們要先跑第六部分的 `/analyze`，把幾份規格的一致性檢查過再實作。這是刻意跟它的建議不一樣的。

# 第六部分：AI × 規格一致性分析

## 6.1 練習：先自己找一個斷點

1. （不要用 AI）打開 `specs/001-meeting-room-booking/e2e-test-plan.md` 的「整合」區塊。

4. 這件事你自己做花了幾分鐘？等一下看機器做要幾秒。

## 6.2 產出一致性報告

1. 在同一個對話貼上：

   ```text
   /analyze

   package: 001-meeting-room-booking
   ```

2. 它會掃描所有產物，不動任何既有檔案，只新增一份報告。

## 6.3 打開 analyze-report.md

1. 打開 `specs/001-meeting-room-booking/analyze-report.md`，從最上面的總表看起。
2. 觀察它的做法：
     - a. 它先把每份產物的穩定 ID 抽出來，做成清單。ID 長這樣：`US-1`、`US1-FR3`、`GR-001`、`S-2-1`、endpoint 名稱。
     - b. 然後兩兩比對「上游有的，下游有沒有落點」。
     - c. 上游有、下游沒有，就是一個推理斷點。
3. 找找看 6.1 你自己找到的那個斷點，報告有沒有抓到？
4. 往下找到覆蓋矩陣。
     - a. 橫軸是什麼？縱軸是什麼？
     - b. 找一個沒被覆蓋的格子，那條需求發生了什麼事？
5. 一條 FR 在 `api-plan.md` 有落點、在測試計畫沒有，代表這條需求「設計了但不會被驗證」。上線後它壞了不會有人知道。

## 6.4 判斷嚴重程度，決定要不要修

1. 看報告裡標了嚴重的項目，試著自己判斷該不該修。
2. 判準只有一句：這條不修，下游會不會產出錯的東西？
3. 舉兩個例子對照：
     - a. 鐵則約束在 `DDL.md` 沒有對應——這是嚴重，因為實作出來就是會超賣。
     - b. 兩份檔案的措辭不同但意思一樣——這是輕微，記下就好。
4. 看報告建議的時候，用這個權重順序：
     - a. 違反憲法 MUST 的，最高。
     - b. 鐵則類需求沒有落到最硬的那一層，例如不可重疊沒進 DDL。
     - c. 上游有、下游沒有的覆蓋缺口。
     - d. 跨層措辭不一致但語意相同。
     - e. 模糊詞、重複描述，最低。這個專案刻意判得很輕，避免噪音蓋掉真問題。
5. 如果它問要不要針對前幾項提出補救編輯建議，回：

   ```text
   要，但先不要自動套用
   ```

6. 它會列建議但不會動你的檔案。報告是唯讀的。
7. 要不要修、修哪幾條，是你決定，不是 AI 決定。這就是人審閘門在最後一站的樣子。

## 6.5 檢查點

1. `analyze-report.md` 存在。
2. 你看得懂覆蓋矩陣在說什麼。
3. 你能講出報告裡至少一條發現，以及它為什麼被判成那個嚴重度。
4. 有嚴重項的話，依報告點名的 skill 重跑修好；時間不夠就記下來，繼續往下。

# 第七部分：AI × 專案實作

## 7.1 下達實作指令

1. 在同一個對話貼上：

   ```text
   /implement

   package: 001-meeting-room-booking
   ```

2. 如果它硬停問你 analyze 的嚴重項要怎麼處理，依講師當下指示選「先修」或「仍要繼續實作」。
3. 出現範圍選單時，回：

   ```text
   1
   ```

   選項是 1 僅後端、2 僅前端、3 後端到前端、4 後端到前端到整合、5 Others。上午只跑後端。

## 7.2 觀察它建環境

1. 它會先親自做第 1 章規格閱讀、第 2 章環境建立，這幾步不委派。
2. 專案本來是空的，所以你會看著後端目錄、資料庫設定、套件、schema、測試基建一個一個長出來。
3. 特別盯 5.2 第 3 步你記下來的那一節——起資料庫。它跑成功了嗎？
4. 這一段是整個第七部分最容易斷的地方。斷了先翻卡關速查，不要急著問。

## 7.3 讓它跑完，不要中途打斷

1. 進第 3 章之後它會開始委派 tdd skill，而且不會停——它從第一個未勾的格子往下一路做，做到整層做完或失敗為止。
2. 所以你沒辦法在中間逐格觀察。讓它跑，跑完再回頭看。
3. 委派的粒度有三種，跑的時候在對話裡看得到：
     - a. red 是一次一個 User Story 整批
     - b. green 是一次一條 Scenario
     - c. refactor 是一次一個 User Story
4. 試著猜測：為什麼 red 可以整批，green 卻要一條一條？

## 7.4 回頭看 Red

1. 跑完之後，打開它生出來的測試檔。
2. 注意第一支不一定是你以為的那支。規格如果有登入，測試計畫會強制產出「登入成功、session 還原、登出後被拒」三條認證基線 Scenario，它們會排在最前面。
3. 找到跟時段衝突有關的那一支，跟 `e2e-test-plan.md` 對應的那條 Scenario 並排看。
     - a. Gherkin 的 Given 變成了測試碼裡的什麼？
     - b. When 變成了什麼？
     - c. Then 變成了什麼？
4. 翻譯關係是一對一的，你追得回去。測試計畫寫「重疊就擋下並提示衝突」，Red 就生出一支打建立預約 API 並斷言衝突狀態碼的測試。
5. 用 5.4 學到的判準，回頭看它跑 Red 那一輪的失敗訊息：那是合格的紅還是爛的紅？

## 7.5 回頭看 Green 與 Refactor

1. 用 `git log --oneline` 跟 `git diff` 看它每一步動了什麼。
2. Green 要盯的不是它寫了什麼，是它動了幾個檔案。
     - a. 為了讓一條 Scenario 變綠，動了幾個檔？
     - b. 合理嗎？
3. 如果為了讓一條情境變綠而改了八個檔案，那就是 1.1 講的第三個痛——你叫它改 A，它順手改壞 B——在小尺度重演。差別在於這次會被立刻看見，不是三週後。
4. Refactor 比對前後的 diff，問一句：這個改動有沒有讓任何一條測試的預期結果改變？
5. 有的話就退回去。那不是 refactor，是偷渡。Refactor 的完成訊號是「什麼都沒變」：行為不變、測試全綠，只有可讀性或結構變好。

## 7.6 收尾

1. 打開 `task-backend.md` 的第 3 章，跑過的那些勾選框被勾起來了。第 4 章的總覽表不會變，那是正常的。
2. 進度是寫在檔案裡的，不是寫在對話裡。
3. 它跑失敗會停在那一格，已經勾的會保留。把錯誤訊息貼回對話，或舉手。
4. 最後自己到終端機再跑一次測試確認。指令在 `task-backend.md` 第 2 章最後那個測試基建小節裡。

## 7.7 一個一定要記住的禁令

1. 不要自己手動呼叫 `/tdd-e2e-red`、`/tdd-e2e-green`、`/tdd-e2e-refactor`。
2. 這三個是被 `/implement` 編排的下游，它們預期收到組好的完整參數：哪個 package、哪個 US、哪條 Scenario、環境狀態。
3. 你手動叫，它拿不到那些參數就會自己猜。
4. 沒有 Red 就直接叫 Green，它會直接寫實作——那就退化成 vibe coding 了，整個 TDD 節奏白做。

# 第八部分：客製化的核心方法

上午你照著我們設計好的流程跑了一遍。接下來要做的是把這個流程改成你們公司的。

重點不是「學會改這六個地方」，而是遇到沒教過的問題時，你找得到問題背後的解法、能舉一反三。

## 8.1 三個教學步驟

1. 用 Prompt 修改 Artifact Example — 先把「產物長什麼樣」改到你滿意。
2. 用 `/artifact-to-skill-engineering` 或 `/skill-engineering` 去反推 skill — 讓 AI 從新的產物長相，反推出「要怎麼引導才生得出這個東西」。
3. 換一個模型（例如 Cursor Composer 2.5）再反推一次，比對兩次推出來的 SKILL.md 差在哪。

為什麼是這個順序：先有你滿意的 Artifact，才有東西可以反推流程。反過來先去改 SOP，你根本不知道要改成什麼樣，只能瞎猜。

第 3 步在 9.1 會實際做一次（那一題的第 12 步）。其餘五題時間夠再做。

## 8.2 客製化的兩條路徑：憲法還是 Skill Rule？

判準一句話：跨 skill、專案統一的規範進憲法；只影響單一 skill 的判準進該 skill 的 rule。

- 「所有查詢 API 都要有分頁參數」→ 跨 skill，進憲法。
- 「每一個資料表都要有 created、updated、deleted 欄位」→ 跨 skill，進憲法。
- 「Red 只允許符合預期的失敗，不得以環境錯誤充數」→ 只影響 `tdd-e2e-red`，進該 skill 的 rule。

分辨錯了的代價：同一條規則在兩個地方重複出現，AI 讀到會困惑，而且改了一邊另一邊會過期。

這個判準也決定 8.3 第 4 段要用哪一個工具：

- 改的是既有 skill → 用 `/artifact-to-skill-engineering`
- 新開一個還不存在的 skill → 用 `/skill-engineering`，因為 `/artifact-to-skill-engineering` 進場要先鎖定既有的 example，新 skill 沒有東西可以鎖
- 改的是憲法 → 用 `/constitution`，因為憲法不是任何 skill 的 template，沒有 example 可以反推

## 8.3 五段式 Prompt 鏈

第九部分的六題不是六種做法，是同一條鏈跑六次。差別只在「從第幾段起手」跟「第 4 段用哪一個工具」。

- 目標已經很明確的題目（第 1 到 3 題）：跳過第 0 段，直接從第 1 段開始。
- 目標還不明確的題目（第 4 到 6 題）：從第 0 段開始，先讓 AI 幫你把意圖翻成具體目標。

每一題的第 0 段、第 3 段、第 4 段、第 5 段要貼什麼，第九部分都會給你當題可以直接複製的完整版本。這一節只是讓你看懂這條鏈長什麼樣，不用從這裡複製。

### 第 0 段　目的對齊

```text
我想要做到：「<把你的意圖填在這裡>」

請先幫我設計「意圖」跟「目標」，並用「意圖」去反推「目標」。

接著我們針對具體目標的可行性進行探討，幫我依照底下的格式列出幾個具體的可行性方案作為選項，讓我選擇我們這次的優化具體目標是什麼，並請依照你的推薦進行排序，越推薦放越上面並寫原因

### 選項 A｜短標
**說明**
一句話說這是什麼
**為什麼**
解決什麼實際開發痛點（誰、什麼時候被卡住、卡多久）
**具體產出**
達成後可觀察的狀態、怎麼驗收
**為何效益高**
跟其他選項比強在哪、代價是什麼
推薦程度：★★★★★｜開發規模：★★★★★

具體目標會先針對各種可行性進行提供探索，而不是相同目標換句話說，原因皆以「開發面」進行說明，並將選項列在對話內讓我做選擇，若你覺得我已經提供給你做法則幫我收斂成格式的產出
```

這一段的重點：AI 只負責把可行性攤開成選項，選哪一個是你決定。

### 第 1 段　查實作方法與細節

```text
好，現在請你幫我查詢所有可能相關的實作方法與細節，依照這些來源進行查詢（相關官方文件、規格手冊 > GitHub 相關實作 Repo（請實際進入專案內查看相關開發內容）> Issues / Discussions 的取捨討論 > 有數據的工程 blog > 相關權威書籍內容），所有內容皆以 Fact 且沒有腦補

完成後，列出實作計畫方案提案，並帶上來源（與連結），讓我選擇

選擇格式與上方相同，只是新增實作步驟與來源欄位
```

來源有優先序，不是隨便查。官方文件在最前面，工程 blog 要有數據才採信。每一條都要帶來源連結，沒有來源的就是腦補。

這一段需要連得到外網。公司網路如果擋 GitHub，這一段跑不動，先跟講師說。

### 第 2 段　收斂成可落地的實作計劃

```text
好，我們決定好了實作方法後，請你針對這個解決方法再往下查出所有實作的細節（實際實作步驟、實際的規範完成的規範有哪些、會遇到什麼問題...），一樣以事實作為驅動，收斂完成成一套可以實際 Step by Step 落地的流程之後，列出你的實作計劃，我等等會用 /clarify skill 釐清細節
```

計劃出來之後，打 `/clarify` 把細節釐清掉再往下。

### 第 3 段　先改 Artifact，不改流程

```text
好，我們一樣使用 Artifact-first 方式開發，先針對 Artifact 進行產出與修改，新增或修改入 Skill 內的 Artifact example，而不針對流程進行修改，等 Artifact 我確認完沒問題後我會使用 /artifact-to-skill-engineering skill 去修改流程
```

這一段一定要指名「這一題的 Artifact 是哪一個檔」，每一題會告訴你。因為不是每個 skill 都有 example——`tdd-e2e-red`、`tdd-e2e-green`、`tdd-e2e-refactor` 三個都沒有 `templates/`，改它們的行為其實是改 `task-plan` 的 example。

這一段結束要人工 Review。Artifact 沒改到你滿意，不要進下一段。

### 第 4 段　把做法收斂進流程

不能只貼一句「收斂進流程」，那樣它不知道要對哪個 skill、拿哪一份 example。要帶參數：

```text
/artifact-to-skill-engineering

target skill：<這一題要改的 skill 名稱>
主要 example：<你剛剛改過的那個 example 檔的完整路徑>

我已確認這份 example 定稿，請收斂做法進入流程。
```

先知道它會停幾次，不然你會以為它卡住：

- 它會先確認 example 是不是真的定稿。這是 MUST 級規則，「看起來差不多」不算定稿。
- 接著它會產一份根因分析報告，等你確認才往下。
- 然後它會產一份 skill engineering plan，再等你確認一次。

也就是這一段不是貼一句就好，是至少三次來回、兩份要讀完的報告。

如果這一題改的是憲法不是 skill，這一段換成 `/constitution`，格式在 9.6 給。

### 第 5 段　開新 Session 驗證

Review 完之後，開一個全新的 Session，自己打那個 skill 的 slash command 跑一次。

不能貼「請呼叫剛剛的 skill」。這些 skill 的設定是 `disable-model-invocation: true`，模型不能自行叫起它們，只有你打 `/` 才會觸發。

每一題會告訴你要打哪一個指令。

一定要開新 Session。在同一個對話裡驗，AI 帶著剛才的上下文，看不出 skill 本身夠不夠自足。

# 第九部分：六個客製化情境

六題的排序是刻意的：從小到大，從解法明確排到解法不明確。

六題走的是同一條鏈，差別只在三件事：起手要不要跑第 0 段、這一題的 artifact 是哪一份、第 4 段用哪一個工具。步數 10 到 12 不等。

## 9.1 第 1 題：如何抽換系統分析產出的 Artifacts？

目標

把現在 `api-plan` 產出的 API markdown 檔，改成 OpenAPI yml 格式。

這一題的 Artifact

`.agents/skills/api-plan/templates/api-plan.example.md`

步驟

1. 開一個全新的對話。
2. 這一題目標已經定了，跳過第 0 段。先貼這一段：

   ```text
   我想要做到：把 api-plan 這個 skill 產出的 API markdown 檔，改成 OpenAPI yml 格式。
   ```

3. 貼 8.3 的第 1 段 Prompt，讓它去查 OpenAPI 3.0 的官方規格與實際實作方式。
4. 它列出實作計畫方案之後，自己選一個。
5. 貼第 2 段 Prompt，讓它收斂成可落地的流程。
6. 打 `/clarify` 把細節釐清掉。
7. 貼第 3 段 Prompt，並指名 artifact：

   ```text
   好，我們一樣使用 Artifact-first 方式開發，先針對 Artifact 進行產出與修改，新增或修改入 Skill 內的 Artifact example，而不針對流程進行修改。

   這一題要改的 example 是 .agents/skills/api-plan/templates/api-plan.example.md

   等 Artifact 我確認完沒問題後我會使用 /artifact-to-skill-engineering skill 去修改流程
   ```

8. 人工 Review 新產出的 example。兩個檢查點：
     - a. 它合不合 OpenAPI 規格？不要用眼睛看，跑指令：

       ```text
       uv run --with openapi-spec-validator python -c "from openapi_spec_validator import validate; import yaml,sys; validate(yaml.safe_load(open(sys.argv[1]))); print('VALID')" <新產出的 yaml 檔路徑>
       ```

     - b. 它有沒有違反憲法？打開 `.constitution/api-plan.md`，逐條對照新 example：資源 ID 是不是字串型 UUID、成功回應有沒有固定 envelope、列表 API 有沒有 `page` 與 `pageSize`。

       這一步比「有沒有漏資訊」有用，因為那份 markdown example 是相簿主題、你的產出是會議室主題，本來就沒辦法逐欄比對。

   ```text
   /artifact-to-skill-engineering
   ```

     - a. `.agents/skills/api-plan/SKILL.md`

     - c. `.agents/skills/api-plan/templates/`
     - d. `.agents/skills/api-plan/scripts/validate_api_plan_output.py`

    ```text
    /api-plan

    ```

12. 換一個模型（Cursor Composer 2.5）重跑第 9 步，比對兩次推出來的 `SKILL.md` 差在哪。差很多就代表這條推理不夠穩，要回頭把 example 改得更明確。

要注意的地方

- 改的是 templates 底下的 example 檔，不是直接去改 SOP。
- 第 10 步 d 那個驗證 script 是硬編 markdown 結構的，產出換成 YAML 之後它 100% 會 fail。要讓 `/skill-engineering` 呼叫 `/skill-derive-script` 把它重寫，這一步漏掉，Phase 5 每次都會報錯。

## 9.2 第 2 題：如何修改 TDD 時每一個步驟的執行方法？

目標

從 Red 著手，把 `/tdd-e2e-red` 的委派粒度，從「一次一個 User Story 整批」改成「一次一條 Scenario」。

為什麼這樣比較好

差別在 just enough 的程度。

- 一次生一整個 User Story 的 Red，AI 要一次考量很多情境，就會過度設計。
- 一條一條增量，小範圍 AI 專注，表現會比較好，也才能真正實踐 just enough。
- 每次 loop 迭代逼出實作設計，跟一次全部做完，長出來的東西不一樣。
- 順帶一提：Green 已經是一條一條了（你在 7.3 第 3 步看過），這一題是把 Red 對齊過去。

這一題的 Artifact

`.agents/skills/task-plan/templates/task-backend.example.md`

`tdd-e2e-red` 這個 skill 沒有 `templates/` 資料夾，它的行為長什麼樣是靠 `task-plan` 產出的格子決定的。所以要改的 example 在 `task-plan` 這邊。

但這一題的槓桿點不在格子形狀，在規則層。先知道現況：`task-plan` 的規則早就要求 Red 一條 Scenario 一格，example 也已經是一條一格。真正還是「整批」的是 `/implement` 委派給 `/tdd-e2e-red` 的方式。所以你在 example 上要新增的，是把「這一格由 implement 逐格委派、不批次」這件事寫成 example 裡看得到的說明，讓下一段反推流程時有東西可依據。

步驟

1. 開一個全新的對話。
2. 目標已經定了，跳過第 0 段。先貼這一段：

   ```text
   我想要做到：把 /tdd-e2e-red 的委派粒度，從「一次一個 User Story 整批」改成「一次一條 Scenario」，跟 Green 對齊。理由是一次生一整個 US 的 Red 會過度設計，一條一條增量才能真正做到 just enough。
   ```

3. 貼第 1 段 Prompt。
4. 選一個方案。
5. 貼第 2 段 Prompt。
6. 打 `/clarify` 釐清細節。
7. 貼第 3 段 Prompt，並指名 artifact 是 `.agents/skills/task-plan/templates/task-backend.example.md`。
8. 人工 Review：格子形狀本來就是一條一格，那不是你的成果。你要確認的是 example 有沒有新增任何一句寫明「這些格子由 implement 逐格委派、不批次」的說明。沒有的話，下一段反推不出東西來。
9. 貼第 4 段，`target skill` 填 `task-plan`。
10. 人工 Review 四個位置：`SKILL.md`、`rules/`、`templates/`、`scripts/`。這一題最關鍵的改動不在 `task-plan`，在 `implement`——打開 `.agents/skills/implement/rules/步驟執行與委派判準.md`，看那條「red 同一 US 批次委派」有沒有被改掉。沒改到就是白做。
11. 開一個全新的 Session，自己打：

    ```text
    /task-plan

    package: 001-meeting-room-booking
    ```

    確認產出的 Red 區塊真的是一條一格。

要注意的地方

- 這一題會連動兩個地方：`task-plan` 產出的格子怎麼切，跟 `implement` 怎麼委派。兩邊要一起改，不然計畫上是三格、執行時是一批，checkbox 對不起來。
- `implement/rules/步驟執行與委派判準.md` 現在明文寫 red 是「同一 US 批次委派」，那一條也要改。

## 9.3 第 3 題：如何修改 TDD 的流程？讓後端能夠掛上資料庫設計的環節？

目標

把 DDL 從「系統分析階段一次產完」，改成「TDD 流程裡每個 User Story 一段增量 migration」。

具體做法是在每個 User Story 的 Red 之前，插入一個 Schema 增量步驟：由這一輪要驗的 Scenario 反推出需要哪些新表、新欄位、新約束，產出一份可回滾的 migration 並套用，跑完才進 Red。

為什麼這樣比較好

- 一次把整個資料庫建完，等於在還沒有任何測試逼出需求之前，就把結構定死了。改成增量之後，每一個欄位都是被某一條 Scenario 逼出來的，沒有人用的欄位不會出現。
- Red 階段有表可打，不會因為缺表而變成 5.4 講的那種「爛的紅」。
- 這條跟第 2 題是同一個道理的兩種應用：都是把「一次做完」改成「一次一個增量」。

這一題的 Artifact

兩個，要一起改：

- `.agents/skills/task-plan/templates/task-backend.example.md`（要多長出 Schema 增量那一格）
- `.agents/skills/data-plan/templates/DDL.example.md`（要從一整份建表腳本改成可分段的 migration）

步驟

1. 開一個全新的對話。
2. 目標已經定了，跳過第 0 段。先貼這一段：

   ```text
   我想要做到：把 DDL 從系統分析階段一次產完，改成 TDD 流程裡每個 User Story 一段增量 migration。在每個 User Story 的 Red 之前插入一個 Schema 增量步驟，由這一輪的 Scenario 反推需要哪些新表、新欄位、新約束，產出可回滾的 migration 並套用，跑完才進 Red。
   ```

3. 貼第 1 段 Prompt。
4. 選一個方案。
5. 貼第 2 段 Prompt。
6. 打 `/clarify` 釐清細節。
7. 貼第 3 段 Prompt，並指名上面那兩個 artifact 檔。
8. 人工 Review：
     - a. `task-backend.example.md` 的每個 US 底下，Red 之前有沒有多一格 Schema 增量？
     - b. `DDL.example.md` 有沒有變成可以一段一段套用的形式，而且每一段都寫得出回滾？
9. 貼第 4 段。這一題要跑兩次，一次 `target skill` 填 `task-plan`，一次填 `data-plan`。
10. 人工 Review 兩個 skill 的 `SKILL.md`、`rules/`、`templates/`、`scripts/`。
11. 開一個全新的 Session，自己打 `/task-plan`，確認產出的 task 檔裡每個 US 的 Red 之前真的多了 Schema 增量那一格。

要注意的地方

- 這一題動的是流程本身（多插一個步驟），不只是某一步的執行方法，比第 2 題大一級。
- migration 要可回滾，不然一條 Scenario 失敗你退不回去。
- `data-plan/rules/DDL單一腳本撰寫判準.md` 現在明文規定「全部建表語句寫在同一個 sql code fence」「不夾帶 migration 工具專屬 DSL」——這兩條跟這一題的目標直接衝突，是必須被改掉的規則。找到它、判斷該不該推翻，就是這一題真正在練的東西。

## 9.5 第 5 題：如何新增新的系統分析步驟？好讓團隊懂得舉一反三？

   ```text
   ### 選項 A｜短標
   **說明**
   一句話說這是什麼
   **為什麼**
   解決什麼實際開發痛點（誰、什麼時候被卡住、卡多久）
   **具體產出**
   達成後可觀察的狀態、怎麼驗收
   **為何效益高**
   跟其他選項比強在哪、代價是什麼
   推薦程度：★★★★★｜開發規模：★★★★★

   具體目標會先針對各種可行性進行提供探索，而不是相同目標換句話說，原因皆以「開發面」進行說明，並將選項列在對話內讓我做選擇，若你覺得我已經提供給你做法則幫我收斂成格式的產出
   ```

3. 它會把「可以新增哪些步驟、各自解決什麼開發痛點、效益多高」攤開成選項，自己選一個。
4. 貼第 1 段 Prompt。
5. 選一個實作方案。
6. 貼第 2 段 Prompt。
7. 打 `/clarify` 釐清細節。
8. 貼第 3 段 Prompt。這一題是全新的步驟，所以 artifact 是一份還不存在的 example，要請它照現有 skill 的 templates 結構新建一份。
9. 人工 Review 新的 example：它的輸入來自上游哪一份產物？輸出要餵給下游誰？這兩件事有沒有寫清楚？
10. 貼第 4 段。這一題是新開一個 skill，所以用 `/skill-engineering` 而不是 `/artifact-to-skill-engineering`。
11. 人工 Review 新 skill 的 `SKILL.md` 與 `rules/`，另外要打開 `.agents/skills/system-analyze/SKILL.md` 的 Phase 4，確認新步驟被插進委派順序裡了。
12. 開新 Session，自己打 `/system-analyze`，確認新步驟真的被跑起來。

要注意的地方

- 這題跟第 4 題的差別：第 4 題是把既有步驟做深，這題是多長一個步驟出來，動到的是流程編排。
- `system-analyze` 的 Phase 4 現在是 data → api → ui 依序委派，而且每一步都「確認檔案存在後才進入下一步」。新步驟要決定插在這三步的哪個位置。

## 9.6 第 6 題：如何修改架構約束？讓 AI 在生成程式碼時必須配合架構約束？

這一題的路線跟前五題不同

架構約束寫在 `.constitution/core.md`，那是憲法不是 skill 的 template，沒有 example 可以反推。所以這一題不走第 3 段跟第 4 段，改走 `/constitution`。

現在的 `core.md` 已經有一批架構約束：monorepo 分 `backend/` 與 `frontend/`、Node.js 加 Express、用 `pg` 手寫 SQL 且禁 ORM 禁 query builder、前端 Vite 且執行期禁 React/Vue/Angular、單一 PostgreSQL、只走 REST 禁 GraphQL 禁 message queue、機密走環境變數。這一題是在這個基礎上改。

步驟

1. 開一個全新的對話。
2. 貼底下這整段：

   ```text
   我想要做到：「修改架構約束，讓 AI 在生成程式碼時必須配合。我想先聽聽看實作的可行性。」

   請先幫我設計「意圖」跟「目標」，並用「意圖」去反推「目標」。

   接著我們針對具體目標的可行性進行探討，幫我依照底下的格式列出幾個具體的可行性方案作為選項，讓我選擇我們這次的優化具體目標是什麼，並請依照你的推薦進行排序，越推薦放越上面並寫原因

   ### 選項 A｜短標
   **說明**
   一句話說這是什麼
   **為什麼**
   解決什麼實際開發痛點（誰、什麼時候被卡住、卡多久）
   **具體產出**
   達成後可觀察的狀態、怎麼驗收
   **為何效益高**
   跟其他選項比強在哪、代價是什麼
   推薦程度：★★★★★｜開發規模：★★★★★

   具體目標會先針對各種可行性進行提供探索，而不是相同目標換句話說，原因皆以「開發面」進行說明，並將選項列在對話內讓我做選擇，若你覺得我已經提供給你做法則幫我收斂成格式的產出
   ```

3. 選一個具體目標。
4. 貼第 1 段 Prompt。這一段在這一題特別重要——架構約束怎麼寫才會真的被 AI 遵守，這件事要有事實依據，不能憑感覺。
5. 選一個實作方案。
6. 貼第 2 段 Prompt。
7. 打 `/clarify` 釐清細節。
8. 不貼第 3、4 段。改成打：

   ```text
   /constitution

   我要修訂 .constitution/core.md 的架構約束，內容是上面收斂出來的實作計劃。
   語意變更請一併升版本並更新最後修訂日期。
   ```

9. 人工 Review `.constitution/` 底下的改動：
     - a. 這條約束是不是真的跨 skill？如果只影響某一個 skill，它應該進那個 skill 的 rule，不是進憲法。用 8.2 的判準判。
     - b. 有沒有跟既有條文重複或打架？
     - c. 版本號跟最後修訂日期有沒有更新？
10. 開一個全新的 Session，自己打受影響的那個 skill 的指令（例如改的是 API 相關約束就打 `/api-plan`），確認 AI 生成時真的遵守了新約束。

要注意的地方

- 這是六題裡解法最不明確的一題，所以排最後。
- 驗收方式要想清楚：怎麼證明 AI 真的照約束生成了？不能只看它嘴上說有遵守，要打開產出的檔案逐條對。
- `core.md` 自己寫明「本檔由人工編輯或 `/constitution` 建立／修訂」，所以走 `/constitution` 才是這個 repo 設計的路。

# 卡關速查

1. 輸入 `/` 找不到 skill：確認 Cursor 開的是 repo 根目錄。
2. `/specify` 一直問問題：正常，最多累計 5 題，同對話回「題號: 選項編號」。

4. `/system-analyze` 卡住不動：它在等你回「繼續」。
5. `/system-analyze` 只產了 plan 就停：那是硬停不是壞掉，看完 3.2、3.3 再回「繼續」。
6. `/e2e-test-plan` 說缺檔：確認 `api-plan.md` 和 `ui-plan.md` 都在。
7. `/task-plan` 說缺檔：確認 `e2e-test-plan.md` 在。
8. `/task-plan` 跑完叫你去 `/implement`：先不要照做，我們要先跑第六部分的 `/analyze`。
9. `/analyze` 說缺必備產物：三份 task 或測試計畫沒產出來，回去補跑。
10. 起資料庫時出現 `Bind for 0.0.0.0:5432 failed: port is already allocated`：你本機已經有東西佔用 5432，很可能是別的專案的容器，或你本機裝過 PostgreSQL。用 `docker ps --filter publish=5432` 找出來停掉，或把 compose 的對外埠改成 55432 並同步改連線設定裡的 port。
11. 起資料庫時出現 `Cannot connect to the Docker daemon`：Docker Desktop 沒開，開起來再跑一次。`docker -v` 有反應不代表 daemon 在跑，要用 `docker ps` 才驗得到。
12. 測試跑起來噴 `ECONNREFUSED`：資料庫沒起，或連線的 port 跟你實際起的對不上。這是爛的紅，先修環境再往下。
13. 想重跑某一步：刪掉那一步的產物檔，重貼該指令，下游要依序重跑。
