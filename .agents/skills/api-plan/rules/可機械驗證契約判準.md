# Rule 1 - 每個契約案例必須有固定欄位與穩定識別

- Level: `MUST`
- `api-plan.md` 的「可機械驗證契約」必須是合法 JSON，頂層包含 `version` 與 `contracts`。
- 每個契約案例必須包含 `contract_id`、`user_story`、`required_evidence`、`method`、`path`、`status`、`request`、`response`。
- `contract_id` 必須在檔內唯一且穩定；method、path 與 status 必須能對到同檔人工可讀的 Endpoint 與 Responses。
- 每個 Responses 標題與測試規劃資料列都必須明列一個 `contract_id`；人工可讀案例與可機械驗證契約必須雙向一一對應，不得只檢查「機械契約能找到人工段落」。
- 每個 Responses 標題下的 JSON 範例都必須實際符合相同 `contract_id` 的 response Schema；只對上 ID 與 status、但欄位形狀或固定值漂移，仍視為契約不一致。
- `api-plan.md` 早於 Scenario 產生，因此不得在此預猜 `scenario_ids`；後續 `e2e-test-plan.md` 與 task 以 `contract_id` 反向引用。

## Good Example

- 這個例子有可追溯案例識別與固定契約欄位。

```json
{
  "contract_id": "API-001-C1",
  "user_story": "US-1",
  "required_evidence": ["backend-contract", "frontend-mock", "integration"],
  "method": "POST",
  "path": "/albums",
  "status": 201,
  "request": {"type": "object"},
  "response": {"type": "object"}
}
```

## Bad Example

- 這個例子只留自由文字，後續無法可靠比對。

```text
建立相簿大概回成功，格式看上面的範例。
```

# Rule 2 - request 與 response 使用可驗證的 JSON Schema 子集

- Level: `MUST`
- `request` 與 `response` 必須是 JSON Schema 物件；本流程至少支援 `type`、`required`、`properties`、`items`、`enum`、`const` 與 `additionalProperties`。
- 無 request body 時使用 `{"type": "null"}`，不可省略欄位。
- 空物件 `{}` 會關閉所有形狀檢查，因此一律禁止；無 body 也不能用空物件代替 `{"type": "null"}`。
- Schema 只描述契約形狀與限制，不把每次執行都會變動的識別、日期或路徑寫成固定範例值。

## Good Example

- 這個例子允許識別值變動，但仍能驗證必要欄位與型別。

```json
{
  "type": "object",
  "required": ["id", "name"],
  "properties": {
    "id": {"type": "string"},
    "name": {"type": "string", "const": "旅行"}
  }
}
```

## Bad Example

- 這個例子把一次性的識別字當成唯一合法 response。

```json
{"id": "alb_only_this_run", "name": "旅行"}
```

# Rule 3 - 必要證據來源由契約案例明確宣告

- Level: `MUST`
- `required_evidence` 只能使用 `backend-contract`、`frontend-mock`、`integration`。
- 只有確實會走該契約案例的層才列為必要來源；完全端對端不必覆蓋所有錯誤案例，但必須覆蓋該 User Story 主路徑涉及的案例。
- 前端 Mock、後端契約測試與整合測試都不得自行改寫 method、path、status、request 或 response；需要改約時先回到 `api-plan.md`。

## Good Example

- 這個例子區分層內錯誤案例與完全端對端主路徑。

```json
[
  {"contract_id": "API-001-C1", "required_evidence": ["backend-contract", "frontend-mock", "integration"]},
  {"contract_id": "API-001-C2", "required_evidence": ["backend-contract", "frontend-mock"]}
]
```

## Bad Example

- 這個例子要求整合層重跑所有局部錯誤切片，混淆兩層目的。

```text
所有 API 錯誤案例一律要求 integration 證據，否則整個故事不能完成。
```
