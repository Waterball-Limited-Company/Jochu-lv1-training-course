# Rule 1 - 雛形不是受測物

- Level: `MUST`
- `system-analyze/ui/*.html` 只供對稿，不是執行期受測物。
- 前端 Scenario 測的是應用程式跑起來的頁面（後端可 Mock，或整合區真串接），不可把靜態雛形檔當成測試入口或斷言對象。
- 這條寫在 skill，不寫進 `e2e-test-plan.md` 正文。

## Good Example

- 這個例子是好的，因為前端對準執行期主頁／相簿詳情。

```md
- **受測部位**
  - 主頁的建立相簿表單
```

## Bad Example

- 這個例子是壞的，因為把雛形 HTML 當受測物。

```md
- **受測部位**
  - 打開 `system-analyze/ui/index.html` 做測試
```

# Rule 2 - 產物給人讀，不寫 skill 備註、不寫引用鏈

- Level: `MUST`
- `e2e-test-plan.md` 是系統開發文件，必須用白話。禁止寫「負責／不負責」、禁止教讀者什麼叫 Fixture、禁止「不是單輪 Red」這類流程旁白。
- US／AC／FR 寫編號加短標題，例如 `US-1 建立相簿並整理照片`、`AC-1-1 建立「旅行」並匯入多格式照片`、`US1-FR1 系統必須允許使用者建立相簿並命名`。禁止只留裸編號，也禁止 `spec.md → 使用者故事 1 → AC-1-1` 這種檔案路徑箭頭鏈。
- 禁止另開 `## 前置資料` 總表或 `FX-*` 代號。前置資料寫在各則對應欄位，用白話（「資料庫尚無任何相簿」「已有空的「旅行」相簿」），不要用「空庫」這種內部暱稱。
- 相簿、照片用名稱（旅行、家庭、工作）。需要對齊 api-plan 時寫日期與張數，不要寫截斷 ID（例如 `alb_…X1`）或「形狀對齊」。
- 證明層已由 `## 後端`／`## 前端`／`## 整合` 承擔。後端／前端欄位名用 **預期 TDD Red**。整合是 US 驗收，不要寫預期 TDD Red。
- **觀測通道** 用白話寫斷言入口。前端寫畫面上哪一區；後端寫哪次 API 讀回；禁止「查資料表」「數 Mock」「打開 `ui/*.html`」。

## Good Example

- 這個例子是好的，因為編號、白話、TDD Red 一眼能讀。

```md
- **US**
  - US-1 建立相簿並整理照片
- **前置資料**
  - 資料庫尚無任何相簿
- **預期 TDD Red**
  - 建立後列表看不到「旅行」
```

## Bad Example

- 這個例子是壞的，因為引用鏈、暱稱、截斷 ID 讓人看不懂。

```md
- **AC / Edge**
  - `spec.md` → 使用者故事 1 → AC-1-1
- **前置資料**
  - 空庫
- **預期紅燈**
  - 建立後列表看不到「旅行」
- **API**
  - `POST /albums` 建立（201 形狀對齊 `alb_…X1`）
```
