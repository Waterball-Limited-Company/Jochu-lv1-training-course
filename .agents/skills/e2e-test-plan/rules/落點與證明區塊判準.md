# Rule 1 - 檔案必須依序包含後端、前端、整合三大證明區塊

- Level: `MUST`
- 正文必須依序出現 `## 後端`、`## 前端`、`## 整合` 三個二級標題。
- 各區塊內以 `### US-* …（優先級：P*）` 分類，其下再放 Scenario。
- 某區塊若本期無 Scenario，仍保留該 `##` 標題，並在區塊說明或假設中交代原因。用正文，不要用引用區塊。

## Good Example

- 這個例子是好的，因為三大區塊齊備，切片用 `S-x-y`，整合用 `US-n`。

```md
## 後端
### US-1 …（優先級：P1）
#### Scenario: S-1-1 …

## 前端
### US-1 …（優先級：P1）
#### Scenario: S-1-1 …

## 整合

對準各 User Story 的獨立驗證方式。真串接、跑執行期畫面，不抄後端／前端的薄 Scenario。

### US-1 …（優先級：P1）
#### Scenario: US-1 …
```

## Bad Example

- 這個例子是壞的，因為仍用單一 US 軸、未切證明區塊。

```md
## US-1 …
### Scenario: S-1-1 …
```

# Rule 2 - 落點：後端／前端寫 AC／Edge 切片；整合寫 User Story 驗收

- Level: `MUST`
- 對每一條 AC／Edge：若理論上前後端都碰得到，必須在 `## 後端` 與 `## 前端` 都寫入對應薄 Scenario（同一業務 ID）。
- `## 整合` 對準 spec 各 User Story 的獨立驗證方式，一則 US 一則真串接驗收。編號用 `US-n`，不要把後端／前端的 `S-x-y` 再抄一輪。
- 邊界切片（不支援格式、只有一本不能拖、禁止巢狀）留在後端／前端，不進整合。
- 主要落點僅互動呈現、後端契約無對應可觀測點時，可只寫前端（例如單一相簿拖放不混淆）。

## Good Example

- 這個例子是好的，因為切片留在前後端，整合寫故事驗收。

```md
## 後端／前端
#### Scenario: S-3-1 拖放後立即新順序
#### Scenario: S-3-2 重整後仍保留順序

## 整合
#### Scenario: US-3 拖放後畫面立即更新且重整後仍保留
```

## Bad Example

- 這個例子是壞的，因為把每條 Edge 都再抄進整合。

```md
Edge-3-1 單一相簿拖放 → 後端、前端、整合全寫
```

# Rule 3 - 後端證明對齊 api-plan；前端對齊 ui-plan；整合兩邊都要

- Level: `MUST`
- 後端 Scenario 的對應欄位必須含 **API**，條列對齊 `api-plan.md` 的 endpoint（可多個）。
- 前端 Scenario 的對應欄位必須含 **UI** 與 **API**；UI 條列對齊 `ui-plan.md` 的頁面／使用者故事／操作 Flow，API 明列所用 Mock endpoint，不碰 API 時固定寫「不適用」。
- 整合 Scenario 必須同時含 **前端**（UI 條列）與 **後端**（API 條列）小標。
- 三層 Scenario 若使用 API，必須以 **API 契約案例** 列出 `api-plan.md` 的穩定契約案例 ID；不使用 API 時明列「不適用」。Scenario 由本階段產生，不得反向要求先產出的 api-plan 預猜 Scenario ID。
- 若同 package 已讀到 `data-plan.md`／`DDL.md`，且該後端或整合 Scenario 涉及可測持久化約束，對應欄位另見 `對應欄位與測試摘要總表判準` 的 **Data** 規則；期望結果須與 `資料合約讀取與對齊判準` 一致。

## Good Example

- 這個例子是好的，因為技術對齊落在對應欄位，不污染 Gherkin。

```md
- **API**
  - `PATCH /albums/reorder` …
  - `GET /albums` …
```

## Bad Example

- 這個例子是壞的，因為把 endpoint 寫進 Gherkin When。

```gherkin
When 使用者呼叫 PATCH /albums/reorder
```

# Rule 4 - 三層必須使用不同但互補的端對端邊界

- Level: `MUST`
- 後端 Scenario 的執行邊界是正式 API → 真後端路由與應用邏輯 → 可重置的測試資料庫或檔案系統；斷言從正式 API response 或正式讀取 API 觀測，不直接查資料表。
- 前端 Scenario 的執行邊界是真瀏覽器 → 執行期前端 → API 邊界；API request match 與 response fixture 必須依 `api-plan.md` 建立 Mock，斷言從執行期 DOM 或使用者可見結果觀測。
- 整合 Scenario 的執行邊界是真瀏覽器 → 真前端 → 真 API → 真後端 → 真資料；對應欄位固定寫 `Mock`＝`停用`、`API`＝`正式 API`，前端明列「真實執行期頁面」、後端明列「真實後端」。開始前必須停用前端 API Mock，且它是 User Story 驗收與回歸，不是另一輪 TDD。
- 整合區塊其他敘述不得與固定欄位矛盾；出現「仍保留／繼續使用／重新啟用／沿用 Mock」或「不會／不需要／無須停用 Mock」時，即使同時保留 `Mock`＝`停用` 也必須失敗。
- 明確維持停用的否定句不是矛盾；例如「Mock 已停用且不會重新啟用 Mock」、「不使用 Mock」必須保留為合法敘述，不能因出現「啟用」或「使用」字樣就誤判。

## Good Example

- 這個例子讓每層各自證明不同風險，最後再證明真串接。

```text
後端 S-1-1：POST /albums → 後端 → 測試 DB → GET /albums
前端 S-1-1：Playwright → Vite 頁面 → api-plan Mock → DOM
整合 US-1：Playwright → Vite 頁面 → 真 API → 後端 → 測試 DB
```

## Bad Example

- 這個例子把元件測試當前端端對端，或在整合驗收繼續使用 Mock。

```text
前端只跑 jsdom 元件測試
整合仍攔截 /albums 並回傳 fixture
```
