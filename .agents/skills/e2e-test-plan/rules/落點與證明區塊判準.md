# Rule 1 - 檔案必須依序包含後端、前端、整合三大證明區塊

- Level: `MUST`
- 正文必須依序出現 `## 後端`、`## 前端`、`## 整合` 三個二級標題。
- 各區塊內以 `### US-* …（優先級：P*）` 分類，其下再放 Scenario。
- 某區塊若本期無 Scenario，仍保留該 `##` 標題，並在區塊說明或假設中交代原因（整合區可用引用說明「本期無整合項」）。

## Good Example

- 這個例子是好的，因為三大區塊齊備且 US 掛在區塊下。

```md
## 後端
### US-1 …（優先級：P1）
#### Scenario: S-1-1 …

## 前端
### US-1 …（優先級：P1）
#### Scenario: S-1-1 …

## 整合
> 僅收 Then 必須真串接才有意義的 Scenario。
```

## Bad Example

- 這個例子是壞的，因為仍用單一 US 軸、未切證明區塊。

```md
## US-1 …
### Scenario: S-1-1 …
```

# Rule 2 - 落點：前後端都碰得到就兩區都寫；整合僅限真串接才有意義

- Level: `MUST`
- 對每一條 AC／Edge：若理論上前後端都碰得到，必須在 `## 後端` 與 `## 前端` 都寫入對應 Scenario（同一業務 ID）。
- `## 整合` 只收 Then 必須前後端真串接後才有意義的例子（例如重整後仍保留順序、跨相簿移動後兩邊一致）；純 API／純 Mock UI 即可證明者不得為了湊數寫進整合。
- 主要落點僅互動呈現、後端契約無對應可觀測點時，可只寫前端（例如單一相簿拖放不混淆）。

## Good Example

- 這個例子是好的，因為持久化重整進整合，立即拖放畫面只進前端。

```md
AC-3-1 拖放後立即新順序 → 僅前端
AC-3-2 重整後仍保留順序 → 後端＋前端＋整合
```

## Bad Example

- 這個例子是壞的，因為把每個 AC 都三區全寫，膨脹且違反整合收斂規則。

```md
Edge-3-1 單一相簿拖放 → 後端、前端、整合全寫
```

# Rule 3 - 後端證明對齊 api-plan；前端對齊 ui-plan；整合兩邊都要

- Level: `MUST`
- 後端 Scenario 的對應欄位必須含 **API**，條列對齊 `api-plan.md` 的 endpoint（可多個）。
- 前端 Scenario 的對應欄位必須含 **UI**，條列對齊 `ui-plan.md` 的頁面／業務邏輯／操作 Flow。
- 整合 Scenario 必須同時含 **前端**（UI 條列）與 **後端**（API 條列）小標。
- 若同 package 已讀到 `data-plan.md`／`DDL.md`，且該後端或整合 Scenario 涉及可測持久化約束，對應欄位另見 `對應欄位與測試摘要總表判準` 的 **Data** 規則；期望結果須與 `資料合約讀取與對齊判準` 一致。

## Good Example

- 這個例子是好的，因為技術對齊落在對應欄位，不污染 Gherkin。

```md
- **API**
  - `PATCH /albums/reorder` …
  - `GET /albums` …
```

## Bad Example

- 這個例子是壞的，因為把 endpoint 寫進 Gherkin When。

```gherkin
When 使用者呼叫 PATCH /albums/reorder
```
