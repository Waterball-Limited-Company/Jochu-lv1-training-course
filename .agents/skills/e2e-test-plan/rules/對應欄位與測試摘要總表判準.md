# Rule 1 - 每則 Scenario 必須有分類小標的「對應欄位」

- Level: `MUST`
- 每則 Scenario 在 Gherkin 區塊之後必須有 `**對應欄位**:` 標題。
- 必須使用分類小標再條列。
- 後端／前端（薄切片）至少含 **US**、**AC / Edge**、**FR**、**受測部位**、**前置資料**、**觀測通道**、**必須維持不變**、**本則不驗證**、**預期 TDD Red**、**API**、**API 契約案例**。前端另需 **UI** 與 **狀態／畫面文案**。前端不碰 API 時，API 與 API 契約案例都固定寫「不適用」；只要 API 不是「不適用」，就必須列出至少一個契約案例 ID。
- 整合（US 驗收）至少含 **US**、**受測部位**、**前置資料**、**觀測通道**、**必須維持不變**、**本則不驗證**、**前端**、**Mock**、**API**、**後端**、**API 契約案例**。每一則整合 Scenario 的 **前置資料** 本身都必須明列可重置測試資料，不能只在章節前言提一次。`Mock` 只能是「停用」，`API` 只能是「正式 API」，前端與後端分別明列真實執行期頁面與真實後端。不要 **預期 TDD Red**，也不必再掛 AC／FR。
- **受測部位** 是 Act 打哪裡；**觀測通道** 是 Assert 從哪條正式介面看。後端寫回應或再 GET；前端寫執行期畫面哪一區；整合兩邊都寫。禁止查資料表、數 Mock、打開雛形 HTML。
- 條列格式為縮排 `- <編號或說明>`。US／AC／FR 都寫編號加短標題，例如 `US-1 建立相簿並整理照片`、`AC-1-1 建立「旅行」並匯入多格式照片`、`US1-FR1 系統必須允許使用者建立相簿並命名`。不可只留裸編號，也不可寫 `檔案 → 章節` 引用鏈。
- **預期 TDD Red** 只寫在後端／前端切片：怎樣算這則還沒做過。哪一端會紅由所在 `##` 區塊決定。
- **前置資料** 用白話寫 Arrange 狀態。細節見 `產物可讀性與雛形非受測判準.md`。

## Good Example

- 這個例子是好的，因為小標齊全且後端含 API。

```md
**對應欄位**:

- **US**
  - US-1 建立相簿並整理照片
- **AC / Edge**
  - AC-1-1 建立「旅行」並匯入多格式照片
- **FR**
  - US1-FR1 系統必須允許使用者建立相簿並命名
- **受測部位**
  - `POST /albums`
- **前置資料**
  - 資料庫尚無任何相簿
- **觀測通道**
  - `POST /albums` 的回應，再讀 `GET /albums`
- **必須維持不變**
  - 不出現子相簿
- **本則不驗證**
  - 批次匯入
- **預期 TDD Red**
  - 建立後列表看不到「旅行」
- **API**
  - `POST /albums` 建立名稱為「旅行」的相簿
```

## Bad Example

- 這個例子是壞的，因為扁平一列、沒有分類小標，也沒有 API／UI。

```md
**對應欄位**:

- US-1 …
- AC-1-1 …
```

# Rule 2 - 涉及持久化約束時後端／整合應補 **Data** 小標

- Level: `SHOULD`
- 當已讀取 `data-plan.md` 與／或 `DDL.md`，且該 Scenario（後端區塊，或整合中依賴真持久化的項）的期望依賴唯一性、必填、關聯／級聯、業務日曆欄位等資料約束時：對應欄位宜增 **Data** 小標，條列對齊的實體／表／約束要旨（仍勿把 SQL 寫進 Gherkin）。
- 純 UI／不碰持久化的前端 Scenario 不需要 **Data**。
- 無 data-plan／DDL 時不強制本小標。

## Good Example

- 這個例子是好的，因為後端衝突 Scenario 標了 Data。

```md
- **API**
  - `POST /bookings` …
- **Data**
  - data-plan：同一會議室時段不可重疊
  - DDL：`bookings` 排除重疊約束要旨
```

## Bad Example

- 這個例子是壞的，因為已讀 DDL 唯一約束，對應欄位卻完全不提 Data。

```md
- **API**
  - `POST /bookings` …
（省略 Data，讀者無法追溯持久化依據）
```

# Rule 3 - 檔末必須有測試摘要總表，一列一條 AC 或 Edge

- Level: `MUST`
- 檔案必須包含 `## 測試摘要總表`。
- 表格欄位固定為 `User Story | AC / Edge | Scenario | 後端 | 前端 | 整合`。
- 一列只對一條 AC 或一條 Edge；同一 Scenario 對到多條時拆成多列。切片表的整合欄一律標 `—`（整合不掛 AC 列）。
- 整合驗收另用「驗收表」列出各 US 的 `US-n` Scenario，欄位固定為 `User Story | Scenario | 整合`。
- 切片表落點欄以 `✓` 或 `—` 標示；FR 不列入本表。

## Good Example

- 這個例子是好的，因為切片表一列一條 AC／Edge、整合欄全是 `—`，驗收表另列 `US-n`。

```md
| User Story | AC / Edge | Scenario | 後端 | 前端 | 整合 |
| --- | --- | --- | --- | --- | --- |
| US-1 | AC-1-1 | S-1-1 | ✓ | ✓ | — |
| US-1 | AC-1-2 | S-1-2 | ✓ | ✓ | — |
| US-1 | Edge-G-2 | S-1-2 | ✓ | ✓ | — |

| User Story | Scenario | 整合 |
| --- | --- | --- |
| US-1 | US-1 建立兩個相簿並確認照片只在所屬相簿 | ✓ |
```

## Bad Example

- 這個例子是壞的，因為把多個 Scenario 併一列，且缺少 AC／Edge 欄。

```md
| Scenario | 後端 | 前端 | 整合 |
| --- | --- | --- | --- |
| S-1-1～S-1-5 | ✓ | ✓ | — |
```

# Rule 4 - 不可再使用「元素覆蓋總表」取代測試摘要總表

- Level: `MUST`
- 檔末落點總覽以「測試摘要總表」為準，不產出「元素覆蓋總表」。
- FR 覆蓋只保留在各 Scenario 的對應欄位，不另開 FR 總表。

## Good Example

- 這個例子是好的，因為檔末只有測試摘要總表與假設。

```md
## 測試摘要總表
…

## 假設
…
```

## Bad Example

- 這個例子是壞的，因為仍保留舊的元素覆蓋總表並與摘要表重複。

```md
## 元素覆蓋總表
| ID | 描述 | Scenario |
```

# Rule 5 - 檔末必須有 blocked 章節與假設章節

- Level: `MUST`
- 必須包含 `## 未產出 Scenario 的邊界（blocked）`；無 blocked 項時表列仍寫 `| （無） | （無） | （無） |`。
- 必須包含 `## 假設`，且為檔案最後一個二級標題；其下至少一條 `- ` 假設。

## Good Example

- 這個例子是好的，因為 blocked 與假設齊備，假設在最後。

```md
## 未產出 Scenario 的邊界（blocked）

| ID | 描述 | 阻塞原因 |
| --- | --- | --- |
| （無） | （無） | （無） |

## 測試摘要總表
…

## 假設

- …
```

## Bad Example

- 這個例子是壞的，因為省略假設或把假設插在摘要表之前。

```md
## 假設
- …

## 測試摘要總表
…
```
