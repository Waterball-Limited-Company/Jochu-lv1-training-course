# Rule 1 - data-plan／DDL 有則必讀，缺檔不阻擋進場

- Level: `MUST`
- 在已確認同 package 的 `api-plan.md`／`ui-plan.md` 可繼續後，必須檢查：
  - `specs/<NNN-plan-package>/system-analyze/data-plan.md`
  - `specs/<NNN-plan-package>/system-analyze/DDL.md`
- 檔案**存在**則必須 READ；用於後續 Scenario 期望與對應欄位對齊。
- 檔案**不存在**時：不因缺 data-plan／DDL 而停止（與 api／ui 缺檔硬停不同）；可在假設註明「本期無資料計畫／DDL」。
- 不可在未檢查路徑的情況下，假設「沒有資料約束」。

## Good Example

- 這個例子是好的，因為有檔就讀、無檔不硬停。

```text
已有 api-plan、ui-plan
存在 data-plan.md、DDL.md → READ 兩者後再展開 Scenario
```

## Bad Example

- 這個例子是壞的，因為有 DDL 卻完全不讀。

```text
只讀 spec／api／ui，跳過 system-analyze/DDL.md
```

# Rule 2 - 後端（及整合之後端側）必須對齊可測的持久化約束

- Level: `MUST`
- 當已讀到 `data-plan.md` 與／或 `DDL.md` 時：寫入 `## 後端`（以及整合 Scenario 中依賴真持久化的 Then）時，MUST 把與該切片或該 US 相關、且可客觀驗證的資料約束反映進期望結果或對應欄位（例如唯一性拒絕、必填／NOT NULL、外鍵／級聯後的可見狀態、業務日曆欄位語意）。
- Gherkin 仍用領域語言，不把 SQL／表名寫進 Given／When／Then；技術對齊放在對應欄位。
- 若某約束僅存在於 DDL／data-plan、且會影響「使用者可觀察結果」，但 api-plan 未寫到：仍須在後端 Scenario 期望或對應欄位標出，並可於假設註明「以 data-plan／DDL 補齊 api 未明示之約束」。
- 與本期 Scenario 無關的 schema 細節不必全數抄入。

## Good Example

- 這個例子是好的，因為唯一約束進後端期望，細節在對應欄位。

```md
Then 系統拒絕建立與既有時段重疊的預約

**對應欄位**:
- **API**: `POST /bookings` …
- **Data**: DDL `bookings` 排除重疊／data-plan 唯一業務鍵 …
```

## Bad Example

- 這個例子是壞的，因為 DDL 有唯一約束，後端 Scenario 卻當成永遠成功。

```md
Then 預約建立成功
（完全忽略 data-plan／DDL 的衝突規則）
```
