# Rule 1 - 第一版做覆蓋、跨層一致性與憲法對齊

- Level: `MUST`
- 偵測軸限定為：
  1. **覆蓋**：需求 ID 是否落到介面／Scenario／Task；Scenario 是否落到對層 task
  2. **跨層一致性**：介面彼此（API↔資料、UI↔API）、e2e 對應欄位引用是否真實存在、相互衝突的約束
  3. **憲法對齊**：當專案根目錄存在 `constitution.md` 時，盤點產物／約束是否違反其中的 MUST（技術基線、整合方式、流程關卡等）；缺 `constitution.md` 時本軸不做（與交付 skill 缺檔警告續跑一致）
- 品質類（模糊形容詞、近似重複需求、文案風格）第一版不做；若極明顯 placeholder（如 `{{PLACEHOLDER}}`、`TODO`）殘留在必讀產物中，可記為**高**或**中**，但不得喧賓奪主。

## Good Example

- 這個例子是好的，因為發現都指向可行動的覆蓋、衝突或違憲。

```text
嚴重：US1-FR4 無任何 API／UI 落點
嚴重：憲法禁止 ORM，data-plan／research 仍採用 ORM
高：e2e 引用 PATCH /photos/:id 但 api-plan 無此路徑
```

## Bad Example

- 這個例子是壞的，因為把大量用詞潤飾當分析主體。

```text
中：多處「必須」可改成「應」
低：兩句 FR 用詞略重複，建議合併修辭
```

# Rule 2 - 覆蓋檢查必須能畫成中文矩陣

- Level: `MUST`
- 至少產出下列可視化總表（欄位名全中文；章節名須對齊 `templates/analyze-report.md`）：
  - **每階段產物盤點表**
  - **問題總表**：編號、比對依據、嚴重程度、位置、摘要、建議處理
  - **規格覆蓋矩陣**：需求編號、摘要、介面落點、Scenario、Task、備註
  - **驗收覆蓋矩陣**：AC／Edge、摘要、Scenario、後端、前端、整合、Task 落點、備註
  - **其餘發現摘要**：主表未列完的次要項合併說明；若無則寫「無。」
- 選備介面不存在且 plan 未要求時，對應欄位標「不適用」，不可標「缺失」混淆缺檔。

## Good Example

- 這個例子是好的，因為欄位可直接 Review，且與報告樣板一致。

```md
| 編號 | 比對依據 | 嚴重程度 | 位置 | 摘要 | 建議處理 |
| --- | --- | --- | --- | --- | --- |
| 一致-1 | 跨層一致性 | 中 | ui-plan.md／api-plan.md | 路徑參數表記不一致 | 統一 `:param` 寫法 |

| 需求編號 | 摘要 | 介面落點 | Scenario | Task | 備註 |
| --- | --- | --- | --- | --- | --- |
| US1-FR4 | 改歸屬為移動 | PATCH /photos/:id | S-1-2 | task-backend | — |

| AC／Edge | 摘要 | Scenario | 後端 | 前端 | 整合 | Task 落點 | 備註 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AC-1-2 | 改加入另一相簿後只留在目標 | S-1-2 | ✓ | ✓ | ✓ | task-backend | — |
```

## Bad Example

- 這個例子是壞的，因為英文縮寫欄位難以給非工程 Reviewer 讀。

```md
| Req Key | Has API? | Task IDs | Notes |
```

# Rule 3 - 嚴重程度指派啟發式

- Level: `MUST`
- **嚴重**：缺必備產物、plan 必跑介面缺檔、核心 FR／AC 零覆蓋且會阻斷基線功能、明顯互相衝突且會讓實作做錯的約束、**產物明顯違反專案根 `constitution.md` 之 MUST**（有憲法檔時）
- **高**：對應欄位引用不存在、介面契約互相矛盾、主要 Scenario 無對層 Task
- **中**：次要覆蓋缺口、術語漂移、非基線路徑的對齊缺口
- **低**：不影響執行順序的輕微備註；第一版應少用
- 問題總數建議以可行動項為主；過多時保留高訊號於「問題總表」，其餘在「其餘發現摘要」合併（對齊省 token）。

## Good Example

- 這個例子是好的，因為嚴重項真的會擋住正確實作或違憲。

```text
嚴重：GR-002 一照片一相簿，但 data-plan 寫成多對多且 api 允許雙重歸屬
嚴重：憲法禁止前端 UI framework，ui-plan／research 仍以 React 為主選型
```

## Bad Example

- 這個例子是壞的，因為把標題用詞差異標成嚴重。

```text
嚴重：spec 寫「相簿」、ui-plan 寫「Album 卡片」
```

# Rule 4 - 問題編號必須穩定可重跑

- Level: `SHOULD`
- 問題編號以比對依據字首＋序號，例如 `覆蓋-1`、`一致-2`（字首對應覆蓋／跨層一致性）。
- 在來源不變時重跑，相同問題應盡量得到相同編號與計數，避免每次亂跳。

## Good Example

- 這個例子是好的，因為編號可對照前後兩次報告。

```text
覆蓋-1、覆蓋-2、一致-1
```

## Bad Example

- 這個例子是壞的，因為編號無語意且不穩定。

```text
F-a、issue#3、tmp-9
```
