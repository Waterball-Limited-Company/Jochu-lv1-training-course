# Rule 1 - 收尾段必須對齊 system-analyze 區塊結構

- Level: `MUST`
- `/analyze` 對話收尾必須包含：任務標題行、規格／主題標題、本輪產物表（產物／路徑／說明）、重點摘要、下一步。
- 標題語意必須是「規格分析已完成」或等價，並可帶功能名。
- 「下一步」必須使用 Speckit 風格散文（可含 skill 路徑），**不可**用可跳過的編號選項清單（例如「1. 先修 2. 或直接實作」）。

## Good Example

- 這個例子是好的，因為結構與 system-analyze 收尾同構，且下一步是散文。

```md
## 規格分析已完成 — 照片相簿整理應用程式

### 本輪產物

| 產物 | 路徑 | 說明 |
| --- | --- | --- |
| 分析報告 | specs/001-photo-albums/analyze-report.md | 覆蓋與一致性發現 |

### 重點摘要

- 嚴重 1 項：… 

### 下一步

本指令在寫入分析報告後結束。請先處理報告中的嚴重項（例如重跑 `/e2e-test-plan` 或修正 `api-plan.md`），完成後再執行 `/implement`。
```

## Bad Example

- 這個例子是壞的，因為用可跳過選項把實作與修規格並列。

```md
建議下一步
1. 修嚴重項
2. 或直接 /implement
```

# Rule 2 - 有嚴重發現時必須強烈建議先修再實作

- Level: `MUST`
- 若報告含「嚴重」等級發現：收尾與報告皆須明確建議**先處理嚴重項後再** `/implement`。
- 必須點名建議動作：重跑哪個 skill，或手動修改哪個來源檔；不可只寫「請自行檢查」。
- 不自動修改任何來源規格；可詢問是否要針對前 N 項提出補救編輯建議，未經使用者同意不得套用。

## Good Example

- 這個例子是好的，因為嚴重閘門清楚且可執行。

```md
偵測到 2 項嚴重發現，建議先處理後再 /implement：
- 缺 ui-plan.md → 請經 /system-analyze 或 /ui-plan 補產
- US1-FR4 零覆蓋 → 請修正 api-plan.md 後視需要重跑 /e2e-test-plan
```

## Bad Example

- 這個例子是壞的，因為有嚴重項仍把實作寫成預設下一步。

```md
下一步請執行 /implement 開始實作。
```

# Rule 3 - 無嚴重項時可建議進入實作，仍應提示剩餘風險

- Level: `SHOULD`
- 若僅有高／中／低或無發現：可建議 Review 報告後執行 `/implement`。
- 若仍有高／中項，應在重點摘要或剩餘風險條列，避免靜默當成完美通過。

## Good Example

- 這個例子是好的，因為放行實作但仍可見剩餘風險。

```md
無嚴重項。可 Review analyze-report.md 後執行 /implement。
剩餘風險：中 1 項術語漂移（見一致-3）。
```

## Bad Example

- 這個例子是壞的，因為有高優先缺口卻完全不提。

```md
分析完成，一切正常，請直接實作。
```

# Rule 4 - 產物表只列本輪實際寫入的分析報告

- Level: `MUST`
- 本輪產物表應列出本次新增或更新的 `analyze-report.md`。
- 不可把唯讀讀過的 `spec.md`、`e2e-test-plan.md` 等來源檔假裝成本輪新增產物。

## Good Example

- 這個例子是好的，因為產物表與實際寫入一致。

```md
| 產物 | 路徑 | 說明 |
| --- | --- | --- |
| 規格分析報告 | specs/001-photo-albums/analyze-report.md | 覆蓋與跨層一致性 |
```

## Bad Example

- 這個例子是壞的，因為把輸入檔當成產出。

```md
| 產物 | 路徑 |
| --- | --- |
| 規格 | specs/001-photo-albums/spec.md |
| 測試計畫 | specs/001-photo-albums/e2e-test-plan.md |
```
