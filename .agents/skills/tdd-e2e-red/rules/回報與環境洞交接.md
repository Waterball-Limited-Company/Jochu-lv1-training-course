# Rule 1 - 成功時必須回報可接續欄位

- Level: `MUST`
- 合格 Red 成功結束時，必須向 implement 回報至少：Scenario ID（與標題）、新測檔路徑、使用的全套跑測指令、本支為合格 Red 的結果摘要（含失敗形態：value difference／expected exception／expected error code）、是否新增／調整了 fixture、helper 或最小骨架。
- 不負責改寫或勾選 `task-*.md` 的 checkbox；進度勾選由 implement 處理。

## Good Example

- 這個例子是好的，因為 implement 能直接接續下一格或 Green。

```text
Scenario: S-1-1
test: backend/tests/s-1-1-create-album-import.test.js
command: npm test（於 backend/）
result: 本支合格 Red（expected error code：期望 201，實得 404）
fixtures: tests/fixtures/sample.jpg, sample.png, sample.webp
skeleton: 無（自然缺路由）
```

## Bad Example

- 這個例子是壞的，因為只說「好了」且順手改 task checkbox。

```text
Red 完成。
（並把 task-backend.md 對應 - [ ] 改成 - [x]）
```

# Rule 2 - 失敗時必須回報卡點類型與缺什麼

- Level: `MUST`
- 失敗停止時必須明確回報卡點類型與缺口。卡點類型應對齊結果五類或進場失敗，例如：缺必填輸入、Scenario 索引失敗、Gherkin 與受測行為矛盾、環境洞、非預期綠、測試本身不可執行且無法收斂為合格 Red。
- 環境洞必須寫清楚要 implement 補什麼，不可含糊說「環境有問題」。

## Good Example

- 這個例子是好的，因為 implement 知道要補哪一步。

```text
卡點: 環境洞
缺: backend/package.json 無 scripts.test，且 tests/ 目錄不存在
請 implement 回到 task 環境建立步驟補測試基建後重呼 /tdd-e2e-red
```

## Bad Example

- 這個例子是壞的，因為失敗原因不可操作。

```text
跑不起來，你自己看一下
```

# Rule 3 - 環境洞只交接、不代修

- Level: `MUST`
- 判定為環境／基建缺口時，本 skill 的職責是停止並交接給 implement，不在本次呼叫中擴大做環境 setup（安裝依賴、建立專案骨架、撰寫正式測試腳本契約等屬 implement／task 環境步驟）。
- 與「最小骨架」的界線以 `Red完成條件與改動邊界.md` 為準；有爭議時優先停止並交回 implement。

## Good Example

- 這個例子是好的，因為只交接、不越權修環境。

```text
回報環境洞 → 結束本次 /tdd-e2e-red
```

## Bad Example

- 這個例子是壞的，因為 Red 順便把整段環境建立做完。

```text
發現沒有 backend/ → 自己 mkdir、npm init、裝 express、寫 schema
```
