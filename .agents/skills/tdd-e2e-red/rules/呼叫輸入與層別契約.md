# Rule 1 - 呼叫時必須帶齊必填欄位

- Level: `MUST`
- implement 呼叫 `/tdd-e2e-red` 時必須顯式提供：`layer`（`backend`／`frontend`／`integration`）、`plan-package`（僅目錄名，如 `001-photo-albums`，**不含** `specs/` 前綴）、單一 **User Story** 識別（如 `US-1`）、該 US 本輪 Red 的 **Scenario 清單**（每一項含 ID／標題與該格**受測行為**）。
- 規格路徑一律寫成 `specs/<plan-package>/...`；不可把已含 `specs/` 的字串再當 `plan-package`。
- 缺少任一必填欄位時必須停止，回報缺什麼，不可自行猜測 `layer`、package 或擅自縮成單一 Scenario 卻不聲明。

## Good Example

- 這個例子是好的，因為 US 與清單齊全，且 `plan-package` 不含 `specs/`。

```text
layer: backend
plan-package: 002-meeting-room-booking
US: US-1
Scenarios:
  - S-1-1 …／受測行為: …
  - S-1-2 …／受測行為: …
→ e2e 路徑: specs/002-meeting-room-booking/e2e-test-plan.md
```

## Bad Example

- 這個例子是壞的，因為缺少 US／清單，卻自行推斷。

```text
Scenario: S-1-1
（自行假設後端、自行搜 specs/）
```

# Rule 2 - 一次呼叫處理單一 US 的 Red 批次；內部仍一次一支

- Level: `MUST`
- 一次 `/tdd-e2e-red` 對應**恰好一個** User Story 的 Red 批次（可含該 US 多個 Scenario）。
- 清單不可跨 US；若 prompt 混入多個 US，必須拒絕並回報。
- **實作顆粒度**：同一呼叫內必須依序處理清單；**一次只撰寫／修正一支** Scenario 測檔，跑測並達成本支合格 Red 後，才可開始下一支。禁止同一步把多支測檔一次寫完再「順便」跑測充數。
- task 上「執行本 User Story 的測試…皆為紅燈」驗紅項由 `/implement` 在批次成功後自行驗證／勾選，**不必**也不應作為本 skill 清單內的 Scenario。

## Good Example

- 這個例子是好的，因為一批一個 US，且內部一支接一支。

```text
US-1 清單 S-1-1→S-1-7
→ 寫 S-1-1 → 跑測 → 合格紅 → 再寫 S-1-2 …
```

## Bad Example

- 這個例子是壞的，因為一次呼叫跨 US，或一次寫完所有測檔。

```text
請把 US-1 與 US-2 的 Red 都做完
（或）先把 S-1-1～S-1-7 測檔全部寫入再第一次跑測
```

# Rule 3 - Scenario 定位失敗時只允許有限度搜尋

- Level: `MUST`
- 應先以 Scenario ID／標題在 `specs/<plan-package>/e2e-test-plan.md` 定位對應區塊。
- 直接定位失敗時，僅允許在**同檔**內以 ID／標題再搜一次；仍找不到必須停止並回報缺的索引，不可改搜其他規格檔或擴大到整 repo。

## Good Example

- 這個例子是好的，因為搜尋範圍仍鎖在同 package 的 e2e-test-plan。

```text
在 specs/001-photo-albums/e2e-test-plan.md 內搜 S-1-2
找不到 → 停止回報
```

## Bad Example

- 這個例子是壞的，因為索引失敗後去翻 `spec.md`／整份 task 補洞。

```text
e2e 找不到就改讀 spec.md 與整份 task-backend.md
```

# Rule 4 - 同 US 清單必須依依賴排序

- Level: `MUST`
- 若清單中存在認證／session 還原／登出等基線 Scenario，或某 Scenario 的受測行為明顯依賴另一支的前置能力，排序時 MUST 讓被依賴項在前。
- 不可為求快把衝突／規則類 Scenario 排到 login 尚未成為清單內已合格紅（或已有足夠最小骨架可走到主斷言）之前，卻仍宣稱後者已合格紅。

## Good Example

- 這個例子是好的，因為先登入基線再業務衝突。

```text
順序: S-auth-login → S-1-1 建立預約 → S-1-2 衝突
```

## Bad Example

- 這個例子是壞的，因為先做衝突測、任其死在 login 404 卻當衝突格完成。

```text
先做 S-1-2（斷言 409），login 仍 404 → 宣告 S-1-2 合格紅
```
