# Rule 1 - Phase 3 起必須先判定實驗路徑（Artifact 或 Skill）

- Level: `MUST`
- 使用者勾選課堂實驗後、撰寫 Prompt 規範前，必須判定本次實驗路徑為下列之一，並寫進 Phase 3 產物抬頭：
  - `Artifact`：有明確來源產物要被 Prompt 直接改寫／抽換（例如 `api-plan.md` → `openapi.yaml`）
  - `Skill`：沒有此類 Artifact；改造對象是既有 skill 的執行方法／流程／約束
- 不可在無 Artifact 時仍寫「修改 Artifact」規範，也不可在有 Artifact 抽換意圖時改走「只改 skill 文案、不碰產物」卻自稱完成抽換實驗。

## Good Example

- 這個例子是好的，因為依課綱槓桿選對路徑。

```text
選項「api-plan → OpenAPI」→ 實驗路徑: Artifact
選項「Green 一次只綠一支」→ 實驗路徑: Skill
```

## Bad Example

- 這個例子是壞的，因為無 Artifact 仍套 Artifact 話術。

```text
改 tdd-e2e-green 推進節奏 → 仍寫「請將此 Artifact 修改為…」
```

# Rule 2 - Artifact 路徑可直接改產物；Skill 路徑禁止直接改 skill

- Level: `MUST`
- **Artifact 路徑**：可用條列式 Prompt 直接改寫來源 Artifact；Phase 4 以同一 Prompt 三 sub-agent 實跑比對產物品質。
- **Skill 路徑**：**禁止**執行者（含本 skill、sub-agent）直接修改目標 skill 的 `SKILL.md`／`rules/`／`templates/`／SOP 流程。改 skill **一定**要走 `/skill-engineering`，且須**交給使用者下指令**（使用者呼叫 `/skill-engineering` 並貼上已確認的 Prompt／修改描述）；執行者只負責設計與交付 Prompt，不得代改正式 skill、也不得用「複製到暫定目錄直接改」假裝完成改 skill。
- 兩條路徑都先設計 Prompt；其後驗證方式依路徑分岔，不可混用。

## Good Example

- 這個例子是好的，因為對象與改法對得上。

```text
Artifact: 「請參照 api-plan.md，將此 Artifact 修改…」→ 三跑產 yaml
Skill: 「請呼叫 /skill-engineering，目標 tdd-e2e-green，符合以下規範…」→ 交付使用者下指令
```

## Bad Example

- 這個例子是壞的，因為 Skill 路徑直接改 skill 檔。

```text
選定 Green 節奏實驗後，sub-agent 直接改 tdd-e2e-green/SKILL.md 或 run-* 複本
```

# Rule 3 - Skill 路徑的 Prompt 必須是給使用者呼叫 /skill-engineering 用的條列描述

- Level: `MUST`
- Skill 路徑的 Prompt 必須寫清：請**呼叫 `/skill-engineering`**，目標 skill、optimize／改執行方法，以及條列修改規範（風格可對齊 Artifact 路徑的條列 Prompt，但入口不是「將此 Artifact 修改」）。
- 不可把 skill 內檔案當成系統分析 Artifact 做抽換話術；不可指示「直接改本目錄 SKILL.md」。
- Phase 4 Skill 路徑的產出是「可交付給使用者的正式 Prompt」，不是三份被直接改過的 skill 目錄。

## Good Example

- 這個例子是好的，因為 Prompt 給使用者下 skill-engineering。

```text
請呼叫 /skill-engineering，目標 skill 為 .agents/skills/tdd-e2e-green/，我們要將此 Skill 優化，符合以下規範：
1. …
```

## Bad Example

- 這個例子是壞的，因為指示直接改 skill 複本。

```text
請參照本 run 目錄內的 tdd-e2e-green，直接改 SKILL.md 與 rules…
```
