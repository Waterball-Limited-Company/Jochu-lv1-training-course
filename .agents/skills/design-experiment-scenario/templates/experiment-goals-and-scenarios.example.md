# Phase 2 (改版格式)｜加強系統分析顆粒度

**範圍**：在某一分析環節加注方法論／更細推理（改 Skill，不是抽換產物）。

---

### 選項 A｜加深 data-plan：實體／欄位萃取推理

**怎麼實作**  
在 `data-plan` 加（或加嚴）規則：每個實體／關鍵欄位都要寫清「FR → 欄位」推理，以及為何獨立成表／合併／不進表。

**為何效益高**  
後端課幾乎人人碰到資料模型；同一份 `data-plan.md` 改前後對照，顆粒度差異一眼可見。

**學員瞬間看懂的點**  
產物還是 `data-plan`，但多了「為什麼這樣建模」——不是換檔，是步驟變細。

實務貼近度：★★★★★｜教學清晰度：★★★★★｜工時風險：中

---

### 選項 B｜加深 api-plan：Endpoint 設計備註

**怎麼實作**  
在 `api-plan` Endpoint 規則加必填清單：驗證、衝突、錯誤語意、冪等等須寫進設計備註（可相對現有 Endpoint 契約規則加厚）。

**為何效益高**  
學員已熟合約檔；加厚備註最能演示「同一 Artifact、推理變密」。

**學員瞬間看懂的點**  
還是那些 API path，但每個 API 的「為什麼這樣設計」變齊了。

實務貼近度：★★★★☆｜教學清晰度：★★★★★｜工時風險：中

---

### 選項 C｜加深 technical-research：選型決策推理

**怎麼實作**  
加嚴 `technical-research`／`plan` 決策條列：每個關鍵選型必須寫候選、取捨軸、為何入選／落選；禁止只留結論無推理。

**為何效益高**  
選型最容易被 AI 寫成口號；加嚴後前後 diff 清楚，對齊「改 Skill 推理密度」。

**學員瞬間看懂的點**  
還是技術研究產物，但每條決策都看得到為什麼。

實務貼近度：★★★★☆｜教學清晰度：★★★★☆｜工時風險：中

---

### 選項 D｜加深 e2e-test-plan：Scenario 與邊界對齊推理

**怎麼實作**  
加嚴 Scenario 產生規則：每個 Scenario 必須寫清對應 AC／邊界來源與「為何需要這支」；禁止無追溯的測項。

**為何效益高**  
測試計畫是 TDD 上游；加厚追溯讓「分析變細」連到可執行規格。

**學員瞬間看懂的點**  
Feature 還在，但每支 Scenario 都掛得回驗收／邊界。

實務貼近度：★★★★☆｜教學清晰度：★★★☆☆｜工時風險：中高

---

### 選項 E｜加深 clarify：高影響缺口提問排序

**怎麼實作**  
加嚴提問排序規則：每題必須標影響面（阻斷實作／僅偏好）與若不問的後果；選項題必須可直接勾選。

**為何效益高**  
釐清環節常流於空問；加嚴後學員看得出「問題變尖」。

**學員瞬間看懂的點**  
還是 clarify，但每題都寫得出「不問會怎樣」。

實務貼近度：★★★☆☆｜教學清晰度：★★★★☆｜工時風險：低

---

### 選項 F｜只加厚 template 章節、不改 rules 判準

**怎麼實作**  
只改某分析 skill 的 template 多幾個標題，不改 rules 的 MUST 判準。

**為何效益高**  
改動小、好當對照保底；但顆粒度「強制力」弱，適合對比什麼才算真正加深。

**學員瞬間看懂的點**  
檔多了幾個空標題——用來對比「有無規則強制推理」。

實務貼近度：★★☆☆☆｜教學清晰度：★★☆☆☆｜工時風險：低
