# Rule 1 - 每份 spec 都必須有規格改動；新建與改／刪寫法不同

- Level: `MUST`
- `spec.md` 必須包含 `## 規格改動`，放在表頭 metadata／輸入需求之後、`## 使用者故事與驗證` 之前。
- 本規格為新建時，規格改動只寫 `- 無（本規格為新建）`。
- 本規格是對既有規格的新增、修改或刪除時，必須列出被影響的既有 `spec.md`，不得省略本節或把改動寫進假設。
- 判定為改／刪時，必須讀取被影響資料夾的 `spec.md`，再填規格改動。

## Good Example

- 這個例子是好的，因為新建把規格改動寫清楚，沒有假裝去改舊規格。

```md
## 規格改動

- 無（本規格為新建）
```

## Bad Example

- 這個例子是壞的，因為缺少規格改動，後續無法從這份 spec 往上追。

```md
**輸入需求**：使用者描述：「刪除隱藏已完成卡片。」

## 使用者故事與驗證 *(必填)*
```

# Rule 2 - 改／刪必須用資料夾 → US → FR → SC，且編號與名稱對齊被改的 spec

- Level: `MUST`
- 每一份被影響的規格以**資料夾名稱**列出，不加 `specs/` 前綴。
- 其下階層固定為 US → FR → SC；每一層都寫該份 spec 裡的編號與名稱，不得只寫編號或自行改名。
- 每個 US 必須標這次對它的關係：新增／修改／刪除／取代。
- 可列多份規格、多個 US／FR／SC；沒有動到的條目不要列。

## Good Example

- 這個例子是好的，因為資料夾、編號、名稱與改動關係都對得回舊 spec。

```md
## 規格改動

- 002-todo-list
  - US4 隱藏已完成卡片（刪除／取代）
    - FR-010 系統必須提供切換是否隱藏已完成卡片
      - SC-004 使用者能隱藏已完成卡片
```

## Bad Example

- 這個例子是壞的，因為只用縮寫、沒有名稱，也沒有說是刪除還是修改。

```md
## 規格改動

- 002
  - US4
```

# Rule 3 - 表頭用規格名稱分行書寫；保留輸入需求；不加來源

- Level: `MUST`
- 表頭欄位名稱是 `規格名稱`，值為本規格資料夾名稱，以 inline code 包住。
- `規格名稱`、`建立日期`、`狀態`、`輸入需求` 各佔一行，不得用 `<br>` 串在同一行。
- 必須保留既有 `輸入需求`（含使用者描述與已拍板的澄清決策）。
- 不得新增「來源」區塊，不得把欄位寫成 `功能分支`。

## Good Example

- 這個例子是好的，因為表頭分行、欄位名稱正確，且輸入需求仍在。

```md
**規格名稱**：`001-photo-albums`
**建立日期**：2026-07-22
**狀態**：草稿
**輸入需求**：使用者描述：「開發一個應用程式，幫助我將照片整理到不同的相簿中。」
```

## Bad Example

- 這個例子是壞的，因為仍用功能分支，並用 `<br>` 把欄位黏在一行。

```md
**功能分支**：`001-photo-albums`<br>**建立日期**：2026-07-22<br>**狀態**：草稿
```
