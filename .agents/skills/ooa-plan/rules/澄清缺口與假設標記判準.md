# Rule 1 - 高影響缺口必須先澄清，或在正文標 `[NEEDS CLARIFICATION]`

- Level: `MUST`
- 若缺口會改變 Actor 集合、Use Case 增刪邊界、領域實體集合／關聯基數，或會改寫關鍵業務成敗條件，優先呼叫 `/clarify`；未拍板前不可寫成看似已確認的定案 OOA。
- 若必須先寫暫定分析供審閱，必須在受影響的 Diagram 備註、UC 敘述或 Sequence 說明內嵌 `[NEEDS CLARIFICATION: …]`，並可在檔末 `## 假設` 註明第一版暫定取捨。
- 標記密度對齊 specify：只標高影響缺口；低風險預設不標標記。

## Good Example

- 這個例子是好的，因為角色能力未決時有標記。

```md
| 主要 Actor | 部門主管 [NEEDS CLARIFICATION: 主管是否可取消他人預約] |
```

## Bad Example

- 這個例子是壞的，因為能力未決卻寫死全圖且無標記。

```md
主管可取消任一員工的預約（之後再問）。
```

# Rule 2 - `[NEEDS CLARIFICATION]` 格式必須與 specify 一致

- Level: `MUST`
- 待澄清標記固定為 `[NEEDS CLARIFICATION: …]`（`NEEDS` 複數），必須明說缺的決策軸。
- 不可使用 `[Need Clarification]`、`[NEED CLARIFICATION]` 等變體作為契約標記。

## Good Example

- 這個例子是好的，因為決策軸清楚。

```md
[NEEDS CLARIFICATION: 設施管理員是否繼承一般預約能力]
```

## Bad Example

- 這個例子是壞的，因為字串不一致且語意含糊。

```md
[NEED CLARIFICATION: 角色之後再說]
```

# Rule 3 - 低風險不確定性只寫檔末「假設」，不打待澄清標記

- Level: `MUST`
- 若缺口不致改變 Actor／UC／領域主結構，可用第一版假設繼續，寫入檔末 `## 假設`（`- ` 條列）。
- 此類低風險項目**不要**使用 `[NEEDS CLARIFICATION]`。
- 澄清後必須回寫相關 `## 假設` 與受影響章節。

## Good Example

- 這個例子是好的，因為表達工具選擇屬低風險假設。

```md
## 假設

- Use Case 圖以 PlantUML 表達；Class／Sequence 用 Mermaid
```

## Bad Example

- 這個例子是壞的，因為把低風險項打成待澄清標記。

```md
[NEEDS CLARIFICATION: Sequence 要用 Mermaid 還是 PlantUML]
```

# Rule 4 - 不可把介面合約或實作選型腦補進 OOA

- Level: `MUST`
- 缺 API 路徑、表結構、框架選型時，不應在 OOA 內發明 endpoint／DDL／技術堆疊充當定案。
- 技術選型缺口應回指 `technical-research.md`／`plan.md`；持久化細節留給 `data-plan`。
- 若業務規則本身不清，用 Rule 1／3 處理，而不是改寫成「先假設用 REST」。

## Good Example

- 這個例子是好的，因為 OOA 停在業務語意。

```md
事後條件：成功則存在已確認預約
```

## Bad Example

- 這個例子是壞的，因為把尚未存在的 API 寫進 UC。

```md
主成功情境：呼叫 POST /api/bookings 回 201
```
