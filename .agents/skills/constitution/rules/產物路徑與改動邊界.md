# Rule 1 - 憲法產物必須寫在 `.constitution/` 約定路徑

- Level: `MUST`
- `/constitution` 的最終產物目錄固定為專案根目錄的 `.constitution/`（相對於 repo root）。
- core 憲法路徑固定為 `.constitution/core.md`。
- skill 憲法路徑固定為 `.constitution/<skill-name>.md`，其中 `<skill-name>` 必須是交付 skill 的目錄／流程名（例如 `api-plan`、`data-plan`），與該 skill 的 `name`／慣用呼叫名對齊。
- 不可寫入 `.agents/`、`specs/`、各 skill 目錄，或其他任意路徑。
- 不可把完成稿只留在聊天訊息中而不寫入檔案。
- 不可再使用已淘汰的專案根目錄單檔 `constitution.md` 作為寫入目標。

## Good Example

- 這個例子是好的，因為輸出落在約定目錄與檔名。

```text
.constitution/core.md
.constitution/api-plan.md
```

## Bad Example

- 這個例子是壞的，因為把憲法放進 skill、specs，或寫回已淘汰的根單檔。

```text
.agents/skills/constitution/constitution.md
specs/001-photo-albums/constitution.md
constitution.md
```

# Rule 2 - 依目標檔分別判定新建或修訂

- Level: `MUST`
- 本次 MUST 先收斂一個或多個寫入目標（`core` 與／或 skill 名）；每個目標各自判定模式。
- 若 `.constitution/<target>.md` 不存在，該目標 MUST 走「新建」：依對應樣板寫出完整初稿。
- 若檔案已存在，該目標 MUST 走「修訂」：在既有內容上更新使用者指定或已收斂的章節，不得無故清空整份無關章節。
- 本 skill 是憲法的寫入方；「交付 skill 缺檔時警告後繼續」不適用於本 skill——對使用者選定且缺檔的目標應新建，而非跳過。

## Good Example

- 這個例子是好的，因為依各目標檔是否存在選擇正確模式。

```text
不存在 .constitution/api-plan.md → 新建完整初稿
已存在 .constitution/core.md → 只修訂相關章節與 metadata
```

## Bad Example

- 這個例子是壞的，因為修訂時把整份檔覆寫成無關空殼，或缺檔時拒絕建立。

```text
已有完整 core，卻用空白樣板整檔覆蓋
使用者要建 api-plan 憲法，卻回報「無憲法可讀」並停止
```

# Rule 3 - 本 skill 不得同步修改其他 skill 或 templates

- Level: `MUST`
- V1 完成條件只包含寫入／更新 `.constitution/` 內本次選定的憲法檔與其 metadata／front matter。
- 禁止為了「憲法變更傳播」而修改其他交付 skill 的 `SKILL.md`、`rules/`、`templates/`，或專案內其他樣板。
- 相依流程之日後掛接（例如各 skill 先 READ 憲法）不在本 skill 職責內。

## Good Example

- 這個例子是好的，因為變更範圍僅限憲法產物。

```text
更新 .constitution/core.md 的技術約束與版本 → 結束
```

## Bad Example

- 這個例子是壞的，因為順便改了其他 skill，超出改動邊界。

```text
更新 .constitution/core.md 後，又去改 implement/SKILL.md 加上 READ 憲法
```

# Rule 4 - 標題、中文 metadata 與 YAML front matter 必須齊全

- Level: `MUST`
- 每份憲法檔最上方 MUST 有 YAML front matter（`---` 包圍），至少包含：
  - `name`：`core` 或對應 skill 名（與檔名一致）
  - `applies_to`：字串陣列；`core` 應列出會讀憲法的交付 skill；skill 憲法至少包含自身 skill 名
- H1：core 固定為 `# 開發規範（憲法）：{{PROJECT_NAME}}`；skill 憲法固定為 `# 開發規範（憲法）：{{SKILL_NAME}}`。
- 中文小標固定分行書寫，至少包含：`**建立日期**:`、`**最後修訂**:`、`**狀態**:`、`**版本**:`；日期為 `YYYY-MM-DD`；版本值以 inline code 包住。
- 不可使用英文 SpecKit 單行格式，也不可加入「功能分支」欄。

## Good Example

- 這個例子是好的，因為 front matter 與中文 metadata 齊全。

```md
---
name: core
applies_to:
  - api-plan
  - data-plan
---

# 開發規範（憲法）：Jochu Lv1 訓練專案

**建立日期**: 2026-07-31
**最後修訂**: 2026-07-31
**狀態**: 生效
**版本**: `2.3.0`
```

## Bad Example

- 這個例子是壞的，因為缺少 front matter，或混用英文治理列並誤加功能分支。

```md
# Constitution

**Version**: 1.0.0 | **Ratified**: 2026-07-31 | **Last Amended**: 2026-07-31
**功能分支**: `001-photo-albums`
```
