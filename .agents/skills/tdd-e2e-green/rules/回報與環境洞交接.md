# Rule 1 - 成功時回報本支 Scenario 變綠摘要

- Level: `MUST`
- 成功結束時必須回報：`layer`、`plan-package`、本支 Scenario ID／標題、使用的全套跑測指令、本支已綠摘要、若有附帶變綠須註明、主要改動的程式路徑（高階即可）。
- 不負責勾選 `task-*.md` checkbox。

## Good Example

- 這個例子是好的，因為 implement 能勾下一格 Green。

```text
Scenario: S-1-1
command: npm test（backend/）
result: 本支綠；既有綠仍綠
incidental: S-1-3（附帶變綠，非本呼叫目標）
touched: src/routes/albums.js
```

## Bad Example

- 這個例子是壞的，因為只說「好了」並代勾 task。

```text
Green 完成。（並勾 task-backend checkbox）
```

# Rule 2 - 失敗時回報卡點與本支狀態

- Level: `MUST`
- 失敗時必須回報卡點類型（缺輸入、Scenario 無法定位、環境洞、回歸弄紅既有綠、本支無法變綠等）、本支／相關仍紅狀態、以及建議 implement 下一步。

## Good Example

- 這個例子是好的，因為回歸與本支分開寫清。

```text
卡點: 回歸
弄紅: S-2-1（先前已綠）
本支: S-1-1 已 PASS 但不可交付
請修復回歸後重呼 /tdd-e2e-green（S-1-1）
```

## Bad Example

- 這個例子是壞的，因為失敗原因不可操作。

```text
有的過有的不過，你再看看
```

# Rule 3 - 環境洞只交接、不代修

- Level: `MUST`
- 環境／基建缺口停止並交回 implement，不在 Green 呼叫中擴大做環境 setup。

## Good Example

- 這個例子是好的，因為只交接。

```text
卡點: 環境洞 — 無 scripts.test → 交回 implement
```

## Bad Example

- 這個例子是壞的，因為 Green 順便重做環境建立章節。

```text
自己 npm init、裝依賴、寫測試腳本後繼續 Green
```
