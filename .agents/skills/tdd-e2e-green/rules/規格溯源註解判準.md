# Rule 1 - 實作必須以 US 為單位寫資料夾名稱／US 編號與名稱，可多行

- Level: `MUST`
- 本 US 落地的實作檔，必須在該 US 的行為接縫上方寫溯源註解，不要每個函式或每個 `if` 都標。
- 格式固定為 `資料夾名稱 / US-N (US名稱)`：資料夾名稱等於本次 `plan-package`，不加 `specs/` 前綴；`US-N` 與名稱對齊本次 User Story。
- 同一檔案承載多個 US 時，每個 US 各寫一行，不得合併成一句。
- 不為了寫這行註解去讀 `spec.md`。

## Good Example

- 這個例子是好的，因為一個 US 只在接縫寫一次，就能從實作對回規格。

```js
// 001-photo-albums / US-1 (建立相簿並整理照片)
```

## Bad Example

- 這個例子是壞的，因為每個內部函式都重複標註，註解比程式碼還多。

```js
// 001-photo-albums / US-1
function validateName() {}
// 001-photo-albums / US-1
function insertAlbum() {}
```

# Rule 2 - 實作註解只指到 US，不寫 FR、SC、來源或規格改動

- Level: `MUST`
- 實作註解只承擔「這段現況實作對應哪份規格的哪個 US」。
- 不得在註解複製 FR／SC 全文、Redmine、使用者原話或規格改動階層。
- 不得把溯源寫進 `e2e-test-plan.md` 或 `task-*.md` 來代替實作註解。

## Good Example

- 這個例子是好的，因為複數 US 就複數行，每行仍只指到 US。

```js
// 005-remove-hide-completed / US-1 (已完成卡片一律可見且固定在下方)
// 005-remove-hide-completed / US-2 (完成與取消完成維持可用)
```

## Bad Example

- 這個例子是壞的，因為把上一份規格的刪除關係整段寫進實作。

```js
// 刪除 002-todo-list US4／FR-010／SC-004；見規格改動
```
