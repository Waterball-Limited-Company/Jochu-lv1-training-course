# Rule 1 - 一次只綠本則；禁止以多支同綠當策略

- Level: `MUST`
- 本次實作目標只有**本則**對應的紅測。
- 禁止把「一次實作讓本 US 多支變綠」當成推進策略或完成條件。
- 若 just enough 實作附帶讓其他既有紅測變綠，可在回報中列出，但不可為了帶綠它們而擴大實作，也不可因此去動「本則不驗證」列出的能力。
- 禁止用放寬斷言、刪測、或改 Gherkin 語意來製造綠燈。

## Good Example

- 這個例子是好的，因為只落地讓 S-1-1 過，不順便做匯入。

```text
本則: S-1-1
本則不驗證: 批次匯入、日期分組、拖放
→ 只做主頁建立表單 → POST /albums
```

## Bad Example

- 這個例子是壞的，因為一次把 S-1-1 與 S-1-6 一起綠掉。

```text
為求快，建立相簿時順便做多檔匯入，讓 S-1-6 也 PASS
```

# Rule 2 - 每步與終態都跑該層全套；守護既有綠燈

- Level: `MUST`
- 每次程式碼實作後必須執行該層**全套**測試（非只跑單支）。
- 本則相關測應變綠；本層在進入本則 Green 前已綠的測試不得被弄紅。
- 本則結束前必須能證明本則測為綠；不要求尚未寫出或標為本則不驗證的測也綠。

## Good Example

- 這個例子是好的，因為全套跑完：S-1-1 PASS，先前已綠仍 PASS。

```text
npm test（frontend 全套）
S-1-1 PASS；沒有其他已綠被弄紅
```

## Bad Example

- 這個例子是壞的，因為只跑單一檔就宣告該 Scenario 完成。

```text
node --test tests/s-1-1.test.js → PASS → 當作一步完成（未跑全套）
```

# Rule 3 - Green 的改動是程式碼實作

- Level: `MUST`
- 本 skill 的主產出是讓本則紅測變綠所需的**程式碼實作**（handler、服務、UI 行為、資料存取等）。
- 可一併修正明顯阻礙執行的測試基建問題（路徑、helper）；但不可把「改測以遷就錯誤實作」當成完成手段。
- 環境／依賴／測試腳本缺失等基建洞交回 implement，不在本次擴大做環境 setup。

## Good Example

- 這個例子是好的，因為實作了本則要求的建立相簿。

```text
落地主頁表單 + POST /albums → S-1-1 變綠
```

## Bad Example

- 這個例子是壞的，因為把預期改成「看不到旅行」來配合半成品。

```text
測期望改成空白主頁，實作什麼都不做 → 假綠
```

# Rule 4 - 只寫剛好通過本則測試的量（just enough）；設計留給 Refactor

- Level: `MUST`
- 每次實作必須是 `just enough code to pass test`：只寫讓**本則**通過所需的最小程式碼，不多寫。
- 必須遵守該格「本則不驗證」：那些能力留給後續 Scenario 的 Red／Green。
- 禁止超寫，至少包含：
  1. 實作時尚**沒有**對應紅測覆蓋、且列在本則不驗證的功能或分支；
  2. 非過測所需的整理、抽共用、優化命名／目錄、預先抽象——這些留給 `/tdd-e2e-refactor`。
- Green 不負責「把設計做對」；本則通過測即可進入該則 Refactor。不可在 Green 以重構／優化為由擴大改動面。

## Good Example

- 這個例子是好的，因為只落地讓 S-1-1 過，未順便做匯入或抽層。

```text
本則: S-1-1
→ 實作建立表單與 POST /albums
→ S-1-1 PASS；不做批次匯入、不抽 AlbumService
```

## Bad Example

- 這個例子是壞的，因為順手做了本則不驗證的功能，或綠了還做設計優化。

```text
為過 S-1-1，順便實作尚未 Red 的匯入，並抽完整 repository 層
```
