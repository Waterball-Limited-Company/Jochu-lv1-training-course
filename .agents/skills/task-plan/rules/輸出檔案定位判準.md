# Rule 1 - 三份產物必須寫到固定路徑

- Level: `MUST`
- `task-plan` 最終產物路徑固定為：
  - `specs/<NNN-plan-package>/task-plan/task-backend.md`
  - `specs/<NNN-plan-package>/task-plan/task-frontend.md`
  - `specs/<NNN-plan-package>/task-plan/task-integration.md`
- 不可寫入 `system-analyze/`，也不可把完成稿只留在聊天或任意檔名中。
- 若 `task-plan/` 尚不存在，應先建立再寫入。

## Good Example

- 這個例子是好的，因為三檔與 `e2e-test-plan.md` 同 package，並落在 `task-plan/`。

```text
specs/001-photo-albums/e2e-test-plan.md
specs/001-photo-albums/task-plan/task-backend.md
specs/001-photo-albums/task-plan/task-frontend.md
specs/001-photo-albums/task-plan/task-integration.md
```

## Bad Example

- 這個例子是壞的，因為把實作計畫與 system-analyze 合約混放。

```text
specs/001-photo-albums/system-analyze/task-backend.md
```

# Rule 2 - `plan-package` 必須與上游 spec 目錄對齊

- Level: `MUST`
- `plan-package` 必須沿用同功能的 `specs/<NNN-plan-package>/` 目錄名。
- 若使用者已指定既有 package，應寫入該 package 的 `task-plan/`，不可另開平行目錄。

## Good Example

- 這個例子是好的，因為 task 與 e2e／plan 同 package。

```text
specs/001-photo-albums/plan.md
specs/001-photo-albums/task-plan/task-backend.md
```

## Bad Example

- 這個例子是壞的，因為跨 package 寫入，追溯會斷開。

```text
specs/001-photo-albums/e2e-test-plan.md
specs/002-other/task-plan/task-backend.md
```

# Rule 3 - 一次執行必須產出後端、前端、整合三檔

- Level: `MUST`
- 單次 `/task-plan` 必須同時產出（或完整覆寫）三份檔案，不可只交其中一層。
- 各檔只涵蓋 `e2e-test-plan.md` 對應 `## 後端`／`## 前端`／`## 整合` 的 Scenario。

## Good Example

- 這個例子是好的，因為三層一次齊全。

```text
task-backend.md + task-frontend.md + task-integration.md
```

## Bad Example

- 這個例子是壞的，因為只交後端，前端／整合缺檔。

```text
僅 task-backend.md
```
