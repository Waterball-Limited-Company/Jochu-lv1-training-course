# Rule 1 - Red 受測行為必須寫清前置、打、看、期望

- Level: `MUST`
- 撰寫 Red 的「受測行為」前，必須閱讀並對齊該層所需上游：`e2e-test-plan`、`plan.md`、`technical-research`、`DDL`／`api-plan`／`ui-plan`（依層）。
- 「受測行為」必須巢狀寫出：`前置`、`打`、`看`、`期望`。後端／前端還必須寫 `還沒做時`；整合可不寫。
- `打`＝打哪（操作或 API）；`看`＝從哪條正式介面觀測（執行期畫面或正式 API，不是雛形檔）。
- 前端若有要比的畫面文案，再加 `文案`；沒有文案可比對時可省略。
- 受測行為 ≠ Gherkin，不套 Given／When／Then；不指定測試手段（如 `supertest`、Mock 框架、fixture 怎麼準備）。
- 不可只寫「去做 S-x-x」而不帶受測行為。

## Good Example

- 這個例子是好的，因為欄位齊全，且觀測通道寫的是執行期主頁。

```md
- 受測行為：
  - 前置：尚未有任何相簿
  - 打：主頁建立相簿表單
  - 看：執行期主頁（不是 `ui/index.html`）
  - 期望：主頁看得到「旅行」
  - 還沒做時：送出後仍顯示還沒有相簿，或看不到「旅行」
```

## Bad Example

- 這個例子是壞的，因為把手段當受測行為，或觀測通道指向雛形檔。

```md
- 受測行為：
  - 以 `supertest` 打 Express app
  - 實作 S-1-1
  - 看：`system-analyze/ui/index.html`
```

# Rule 2 - Green 必須寫本則不驗證；Refactor 只整理這一則

- Level: `MUST`
- Green 的「實作計畫」必須寫明動哪些 API 或頁面／互動、用什麼方式落地、對齊哪些契約或約束，並以 `本則不驗證：` 列出這一則不做的下一則能力。
- Refactor 的「整理範圍」必須寫清只整理這一則剛綠的碼，並寫 `不准擴到` 本則不驗證／下一則。
- 不可把 Green 寫成「讓本 US 既有 Red 全綠」，也不可讓 Refactor 一次整理整個 US。

## Good Example

- 這個例子是好的，因為 Green 劃清本則邊界，Refactor 只清這一則。

```md
- 實作計畫：
  - 主頁建立表單 → `POST /albums` → 執行期主頁出現「旅行」
  - 本則不驗證：批次匯入、日期分組、拖放
- 整理範圍：
  - 在綠燈下整理剛寫的建立表單／`POST /albums` 命名與去重
  - 不准擴到批次匯入、日期分組、拖放
```

## Bad Example

- 這個例子是壞的，因為一次綠整包 US，或 Refactor 擴到下一則。

```md
- 實作計畫：
  - 讓本 US 既有 Red 全綠
- 整理範圍：
  - 整理本 US 全部頁面與下一個 Scenario 的匯入
```

# Rule 3 - 環境建立必須從 plan／research 推導，且止於可跑底座

- Level: `MUST`
- §2 環境建立必須對齊 `plan.md` 專案結構與 `technical-research` 技術選型（工具版本、目錄、依賴、schema／proxy、測試基建、smoke）。
- 可含必要驗證指令；不可貼業務程式碼、大段 heredoc 產品實作，或逐步「預期結果」說明區塊。
- 測試入口是執行期應用（後端 API、前端 Vite 頁面），不可把 `system-analyze/ui/*.html` 當測試入口。
- 本節不可偷做故事功能（例如建立「旅行」、平鋪匯入、拖放排序）。
- 整合層環境以「真串接可跑」為主，不重搭前後端專案。

## Good Example

- 這個例子是好的，因為步驟對齊 plan，停在 smoke，且禁止偷做故事。

```md
### 2.3 測試／驗收基建
- [ ] 測試入口為執行期 Vite 頁面（`frontend/`）；不要把 `system-analyze/ui/*.html` 當測試入口
- [ ] 最小 smoke：頁面可載入、進入點可執行
- [ ] 本節不可做出「旅行」相簿或平鋪匯入
```

## Bad Example

- 這個例子是壞的，因為在環境章節寫入業務路由，或把雛形當測試入口。

```md
- [ ] 實作 POST /albums 完整 handler 與錯誤碼分支
- [ ] 用 `system-analyze/ui/index.html` 當前端測試入口
- [ ] 先建好「旅行」相簿方便後面 Scenario
```

# Rule 4 - 意圖級細節，不寫可執行產品程式碼

- Level: `MUST`
- task 產物只寫受測行為／實作意圖與 step-by-step 導航；產品／測試程式碼細節留給 `/tdd-e2e-red`、`/tdd-e2e-green`、`/tdd-e2e-refactor` 執行時展開。
- 可點名模組／函式檔邊界（如 `multer`、`dnd.js`）、endpoint、狀態碼與契約對齊句。
- 不可嵌入完整實作原始碼區塊作為「照抄完成」的產品行為。

## Good Example

- 這個例子是好的，因為點名落地邊界但不貼完整程式。

```md
- 落地 `POST /albums/:albumId/photos`：multer 收多檔、MIME 限 JPEG／PNG／WebP、sharp 縮圖
```

## Bad Example

- 這個例子是壞的，因為把完整 route handler 原始碼貼進 task 檔當照抄答案。

```md
- 把 `app.post('/api/albums', …)` 的完整函式本體貼進文件
```

# Rule 5 - AC／Edge 與 Scenario 必須追溯上游，不腦補

- Level: `MUST`
- 各 US 的 `AC / Edge` 必須來自 `e2e-test-plan`（或同 package `spec`）對應該層 Scenario 的對應欄位。
- 後端／前端的區塊 ID 集合必須與 `e2e-test-plan.md` 該 `##` 區塊的 `S-n-m` 一致，不可增刪未對齊項。
- 整合的區塊 ID 集合必須與 e2e `## 整合` 的 `US-n` 一致；不可把切片 `S-n-m` 再抄進整合。

## Good Example

- 這個例子是好的，因為後端只列 e2e `## 後端` 的 `S-n-m`，整合只列 `US-n`。

```text
後端 e2e：S-1-1、S-1-6…（無 S-3-1）
task-backend：同一集合
整合 e2e：US-1～US-4
task-integration：同一集合
```

## Bad Example

- 這個例子是壞的，因為把僅前端的 S-3-1 寫進後端，或把 S-1-2 抄進整合。

```text
task-backend 含 S-3-1
task-integration 含 S-1-2、S-3-2
```
