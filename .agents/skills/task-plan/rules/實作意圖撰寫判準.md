# Rule 1 - 必須依上游規格推導 Red 受測行為與 Green 實作計畫，不可只列 Scenario 標題

- Level: `MUST`
- 撰寫 Red 的「受測行為」或 Green 的「實作計畫」前，必須閱讀並對齊該層所需上游：`e2e-test-plan`、`plan.md`、`technical-research`、`DDL`／`api-plan`／`ui-plan`（依層）。
- **Red（受測行為）**：只寫要驗證什麼——呼叫／流程與期望結果（含狀態碼或等價斷言）；不指定測試手段（如 `supertest`、Mock 框架、fixture 怎麼準備）。受測行為 ≠ Gherkin，不套 Given／When／Then。
- **Green（實作計畫）**：寫明動哪些 API 或頁面／互動、用什麼方式落地、對齊哪些契約或約束。
- 不可只寫「去做 S-x-x」或「讓本 US Red 全綠」而不帶受測行為或按 Scenario 拆開的實作意圖。

## Good Example

- 這個例子是好的，因為 Red 只寫期望、Green 才寫落地手段。

```md
- 受測行為：
  - `POST /api/albums` 建立相簿 → 預期 201
  - `POST /api/albums/:albumId/photos` 一次上傳多檔 JPEG／PNG／WebP → 預期 201
  - `GET /api/albums` 可見該相簿；`GET /api/albums/:albumId/photos` 含剛上傳照片
- 實作計畫：
  - 落地 `POST /albums`：寫入 `albums`（DDL）、`name` 驗證
  - 落地 `POST /albums/:albumId/photos`：multer 收多檔、MIME 限 JPEG／PNG／WebP
```

## Bad Example

- 這個例子是壞的，因為 Red 寫成「照著做」手段，或沒有從規格推導。

```md
- 受測行為：
  - 以 `supertest` 打 Express app
  - 實作 S-1-1
  - 參考規格自行決定
```

# Rule 2 - 環境建立必須從 plan／research 推導，且止於可跑底座

- Level: `MUST`
- §2 環境建立必須對齊 `plan.md` 專案結構與 `technical-research` 技術選型（工具版本、目錄、依賴、schema／proxy、測試基建、smoke）。
- 可含必要驗證指令；不可貼業務程式碼、大段 heredoc 產品實作，或逐步「預期結果」說明區塊。
- 整合層環境以「真串接可跑」為主，不重搭前後端專案。

## Good Example

- 這個例子是好的，因為步驟對齊 plan，且停在 smoke／連線證明。

```md
### 2.2 套件與腳本
- [ ] 初始化 ESM，安裝 express／multer／better-sqlite3／sharp
- [ ] `npm test` 指向 `node --test`
```

## Bad Example

- 這個例子是壞的，因為在環境章節寫入業務路由實作細節。

```md
- [ ] 實作 POST /albums 完整 handler 與錯誤碼分支
```

# Rule 3 - 意圖級細節，不寫可執行產品程式碼

- Level: `MUST`
- task 產物只寫受測行為／實作意圖與 step-by-step 導航；產品／測試程式碼細節留給 `/implement` 執行 task 時，再依步驟委派 `/tdd-e2e-red`（同一 US 批次）、`/tdd-e2e-green`、`/tdd-e2e-refactor` 展開。
- 可點名模組／函式檔邊界（如 `multer`、`dnd.js`）、endpoint、狀態碼與契約對齊句。
- 不可嵌入完整實作原始碼區塊作為「照抄完成」的產品行為。
- 不可把「留給 tdd-e2e 系列展開」解讀成 `/task-plan` 交付後應直接呼叫那些 skill；執行入口固定為 `/implement`（細節見 `交付與下游交接判準.md`）。
- 不可把「US 批次 Red」解讀成一次寫完多支測檔再不跑測；批次只改委派粒度，測檔仍一支一跑（見 `/tdd-e2e-red`）。

## Good Example

- 這個例子是好的，因為點名落地邊界但不貼完整程式，且執行鏈經 implement。

```md
- 落地 `POST /albums/:albumId/photos`：multer 收多檔、MIME 限 JPEG／PNG／WebP、sharp 縮圖
- （執行時由 `/implement` 勾到對應 `/tdd-e2e-green` 步驟再展開程式）
```

## Bad Example

- 這個例子是壞的，因為把完整 route handler 原始碼貼進 task 檔當照抄答案。

```md
- 把 `app.post('/api/albums', …)` 的完整函式本體貼進文件
```

# Rule 4 - AC／Edge 與 Scenario 必須追溯上游，不腦補

- Level: `MUST`
- 各 US 的 `AC / Edge` 必須來自 `e2e-test-plan`（或同 package `spec`）對應該層 Scenario 的對應欄位。
- 各層 Red 的 Scenario ID 集合必須與 `e2e-test-plan.md` 該 `##` 區塊一致，不可增刪未對齊項。
- 整合僅涵蓋 e2e `## 整合` 列出的 Scenario。

## Good Example

- 這個例子是好的，因為後端 Red 只列 e2e `## 後端` 的 ID。

```text
後端 e2e：S-1-1…S-4-2（無 S-3-1）
task-backend Red：同一集合
```

## Bad Example

- 這個例子是壞的，因為把僅前端的 S-3-1 寫進後端 task。

```text
task-backend Red 含 S-3-1
```
