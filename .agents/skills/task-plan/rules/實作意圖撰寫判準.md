# Rule 1 - 必須依上游規格推導實作計畫，不可只列 Scenario 標題

- Level: `MUST`
- 撰寫 Red／Green 的「實作計畫」前，必須閱讀並對齊該層所需上游：`e2e-test-plan`、`plan.md`、`technical-research`、`DDL`／`api-plan`／`ui-plan`（依層）。
- 每條實作計畫應寫明：動哪些 API 或頁面／互動、用什麼方式證明或落地、對齊哪些契約或約束。
- 不可只寫「去做 S-x-x」或「讓 Red 全綠」而不帶實作意圖。

## Good Example

- 這個例子是好的，因為從 api-plan／DDL 推出具體 API 與方式。

```md
- 實作計畫：
  - 以 `supertest` 打 Express app，路徑前綴 `/api`
  - 串 `POST /albums` → `POST /albums/:albumId/photos` multipart
  - 契約對齊 api-plan；DB 依 DDL `albums`→`photos`
```

## Bad Example

- 這個例子是壞的，因為沒有從規格推導，執行者仍需自己重讀全部合約。

```md
- 實作計畫：
  - 實作 S-1-1
  - 參考規格自行決定
```

# Rule 2 - 環境建立必須從 plan／research 推導，且止於可跑底座

- Level: `MUST`
- §2 環境建立必須對齊 `plan.md` 專案結構與 `technical-research` 技術選型（工具版本、目錄、依賴、schema／proxy、測試基建、smoke）。
- 可含必要驗證指令；不可貼業務程式碼、大段 heredoc 產品實作，或逐步「預期結果」說明區塊。
- 整合層環境以「真串接可跑」為主，不重搭前後端專案。

## Good Example

- 這個例子是好的，因為步驟對齊 plan，且停在 smoke／連線證明。

```md
### 2.2 套件與腳本
- [ ] 初始化 ESM，安裝 express／multer／better-sqlite3／sharp
- [ ] `npm test` 指向 `node --test`
```

## Bad Example

- 這個例子是壞的，因為在環境章節寫入業務路由實作細節。

```md
- [ ] 實作 POST /albums 完整 handler 與錯誤碼分支
```

# Rule 3 - 意圖級細節，不寫可執行產品程式碼

- Level: `MUST`
- task 產物只寫實作意圖與 step-by-step 導航；產品／測試程式碼細節留給 `/tdd-e2e-red`、`/tdd-e2e-green`、`/tdd-e2e-refactor` 執行時展開。
- 可點名模組／函式檔邊界（如 `multer`、`dnd.js`）、endpoint、狀態碼與契約對齊句。
- 不可嵌入完整實作原始碼區塊作為「照抄完成」的產品行為。

## Good Example

- 這個例子是好的，因為點名落地邊界但不貼完整程式。

```md
- 落地 `POST /albums/:albumId/photos`：multer 收多檔、MIME 限 JPEG／PNG／WebP、sharp 縮圖
```

## Bad Example

- 這個例子是壞的，因為把完整 route handler 原始碼貼進 task 檔當照抄答案。

```md
- 把 `app.post('/api/albums', …)` 的完整函式本體貼進文件
```

# Rule 4 - AC／Edge 與 Scenario 必須追溯上游，不腦補

- Level: `MUST`
- 各 US 的 `AC / Edge` 必須來自 `e2e-test-plan`（或同 package `spec`）對應該層 Scenario 的對應欄位。
- 各層 Red 的 Scenario ID 集合必須與 `e2e-test-plan.md` 該 `##` 區塊一致，不可增刪未對齊項。
- 整合僅涵蓋 e2e `## 整合` 列出的 Scenario。

## Good Example

- 這個例子是好的，因為後端 Red 只列 e2e `## 後端` 的 ID。

```text
後端 e2e：S-1-1…S-4-2（無 S-3-1）
task-backend Red：同一集合
```

## Bad Example

- 這個例子是壞的，因為把僅前端的 S-3-1 寫進後端 task。

```text
task-backend Red 含 S-3-1
```
