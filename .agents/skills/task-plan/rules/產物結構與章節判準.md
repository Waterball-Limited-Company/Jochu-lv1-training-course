# Rule 1 - 每檔固定五個一級章節

- Level: `MUST`
- 每份 task 檔必須依序包含：
  1. `## 1. 規格閱讀`
  2. `## 2. 環境建立`
  3. `## 3. User Story 實作計劃`
  4. `## 4. 進度總覽`
  5. `## 5. 假設`
- 不可使用英文 `Setup` 作為 §2 標題。
- 不可另加「完成定義」類章節或逐步「預期結果」區塊。

## Good Example

- 這個例子是好的，因為章節順序與命名固定。

```md
## 1. 規格閱讀
## 2. 環境建立
## 3. User Story 實作計劃
## 4. 進度總覽
## 5. 假設
```

## Bad Example

- 這個例子是壞的，因為用英文 Setup，且夾了完成定義章節。

```md
## 2. Setup Phase
## 5. 後端完成定義
## 6. 假設
```

# Rule 2 - 後端與前端每則 Scenario 由同一代理跑完三階段與層內全綠

- Level: `MUST`
- §3 下每個 User Story 使用 `### US-n …（優先級：Pn）`。
- 每個 US 必須先有 `#### AC / Edge`，接著依該 US 在本層的 Scenario **各開一個區塊**。
- 後端／前端區塊標題為 `#### S-n-m <標題>`。
- 每個區塊內必須依序有四個 checkbox：`/tdd-e2e-red` → `/tdd-e2e-green` → `/tdd-e2e-refactor` → `User Story 層內全綠閘門`。
- 四個 checkbox 是同一個 Scenario Agent 的單一生命週期；不得在三個 TDD 階段間重開代理。層內全綠必須跑同層、同 User Story 到目前為止已建立的所有 Scenario 測試。
- 每個 User Story 的最後一個 Scenario 後必須另有 `User Story 完成閘門`，執行該故事完整測試與該層全套回歸。
- 不可使用 US 級 `#### Red`、`#### Green`、`#### Refactor` 把多則 Scenario 收成三大段。
- 一則 Scenario 做完 Red → Green → Refactor 後，才進入下一則；不可一個 US 先整包 Red 再整包 Green。

## Good Example

- 這個例子是好的，因為 AC／Edge 之後每則各自一區塊 RGB。

```md
### US-1 建立相簿並整理照片（優先級：P1）

#### AC / Edge

- AC-1-1 …

#### S-1-1 建立名為「旅行」的相簿

- [ ] `/tdd-e2e-red` — S-1-1 建立名為「旅行」的相簿:
  - 受測行為：
    - …
- [ ] `/tdd-e2e-green` — S-1-1:
  - 實作計畫：
    - …
- [ ] `/tdd-e2e-refactor` — S-1-1:
  - 整理範圍：
    - …
- [ ] `User Story 層內全綠閘門` — S-1-1:
  - 執行：同層 US-1 到目前為止的全部 Scenario 測試
  - 完成：全部為綠，契約證據也通過
- [ ] `User Story 完成閘門` — US-1:
  - 執行：US-1 完整測試，再跑該層全套回歸
```

## Bad Example

- 這個例子是壞的，因為用 US 級三大段把多則 Scenario 收成一輪。

```md
### US-1 建立相簿並整理照片（優先級：P1）
#### AC / Edge
#### Red
- [ ] `/tdd-e2e-red` — S-1-1 …
- [ ] `/tdd-e2e-red` — S-1-6 …
#### Green
#### Refactor
```

# Rule 3 - 整合只做 User Story 完全端對端驗收

- Level: `MUST`
- 整合區塊標題為 `#### US-n <驗收標題>`，底下只能有一個 `User Story 完全端對端驗收` checkbox。
- 驗收內容必須包含前置閘門，以及固定欄位 `Mock：停用`、`前端：真實執行期頁面`、`API：正式 API`、`後端：真實後端`，再列可重置資料、真瀏覽器完整路徑、正式觀測通道、執行命令、契約證據與失敗路由。不得用同段其他關鍵字掩蓋「仍保留 Mock」等矛盾內容。
- 整合區塊不得包含 `/tdd-e2e-red`、`/tdd-e2e-green`、`/tdd-e2e-refactor`，也不得描述預期 Red。

## Good Example

- 這個例子是好的，因為整合只執行真串接驗收。

```md
- [ ] `User Story 完全端對端驗收` — US-1:
  - 前置閘門：後端與前端 US-1 完成閘門皆已通過
  - Mock：停用前端 API Mock
  - 執行：Playwright 跑真前端 → 真 API → 真後端 → 可重置資料
  - 失敗路由：行為缺口回 Scenario；契約漂移依 api-plan 判定；接線缺陷建立整合回歸
```

## Bad Example

- 這個例子是壞的，因為整合又被包成一輪假的 TDD。

```md
- [ ] `/tdd-e2e-red` — US-1 預期先失敗
- [ ] `/tdd-e2e-green` — US-1 修到通過
- [ ] `/tdd-e2e-refactor` — US-1 順便整理接線
```
