# Rule 1 - 交付結束時下一步必須指向 `/implement`

- Level: `MUST`
- `/task-plan` 完成驗證並向使用者交付三份 `task-*.md` 時，對話「下一步」MUST 明確導向 `/implement`（可註明 package 與可選層別範圍）。
- MUST 說明：`task-*.md` 由 `/implement` 逐步勾選執行；§1／§2 由 implement 親自落地；標有 `/tdd-e2e-red` 的 **Scenario 格**由 implement **按 US 批次**委派（內部一支一測），`/tdd-e2e-green` 按 Scenario 委派，`/tdd-e2e-refactor` 按 US 委派。
- MUST NOT 建議使用者或本 agent「直接依序呼叫」`/tdd-e2e-red` → `/tdd-e2e-green` → `/tdd-e2e-refactor` 作為 task-plan 完成後的主路徑。

## Good Example

- 這個例子是好的，因為下一步鎖在 implement，並釐清 TDD skill 只經委派。

```md
下一步

三份實作計畫已就緒。請執行 `/implement`（package：`002-meeting-room-booking`），由它依 `task-*.md` 勾選前進；其中的 `/tdd-e2e-red` 等標籤是委派步驟，不要在對話中直接當下一指令依序呼叫。
```

## Bad Example

- 這個例子是壞的，因為跳過 implement、把 checkbox 標籤當成使用者下一句指令。

```md
下一步可依 US 順序跑 `/tdd-e2e-red` → `/tdd-e2e-green` → `/tdd-e2e-refactor`。
```

# Rule 2 - Checkbox 上的 tdd-e2e 標籤僅供委派

- Level: `MUST`
- `task-*.md` 內 `` `/tdd-e2e-red` ``、`` `/tdd-e2e-green` ``、`` `/tdd-e2e-refactor` `` 是給 `/implement` 辨識並委派的步驟標籤，不是要求使用者在聊天中直接輸入的 skill 指令序列。
- 交付摘要、假設章或口頭說明若提及這些標籤，MUST 同時交代「經 `/implement` 委派」，避免單獨列出成「建議下一步 skill」。

## Good Example

- 這個例子是好的，因為標籤語意與執行入口綁在一起。

```md
- 假設：Red／Green／Refactor 列上的 tdd-e2e 標籤僅供 `/implement` 委派，不作為對話下一指令。
```

## Bad Example

- 這個例子是壞的，因為把標籤講成可獨立啟動的流程入口。

```md
計畫寫好了，請開始 `/tdd-e2e-red`。
```

# Rule 3 - 交付段必須條列產物路徑並禁止「或直接實作」跳過 implement

- Level: `SHOULD`
- 交付時 SHOULD 條列三檔路徑（`task-backend.md`／`task-frontend.md`／`task-integration.md`）與 validator 通過狀態。
- MUST NOT 寫「或直接實作／跳過 implement／自行跑 TDD」等可跳過編排器的選項。

## Good Example

- 這個例子是好的，因為產物清楚且入口唯一。

```md
產物：`task-plan/task-backend.md`、`task-frontend.md`、`task-integration.md`（validator OK）。
下一步：`/implement`。
```

## Bad Example

- 這個例子是壞的，因為提供跳過 implement 的旁路。

```md
可 `/implement`，或直接實作／自行跑 red-green-refactor。
```
