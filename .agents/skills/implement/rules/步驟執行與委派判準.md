# Rule 1 - 控制面步驟由 implement 親自執行

- Level: `MUST`
- 規格閱讀、環境建立、User Story 完成閘門、整合完全端對端驗收與 task 勾選，均由 `/implement` 親自執行。
- 不可把環境建立塞進 Red，也不可期待 Scenario Agent 修改 task 檔。

## Good Example

```text
implement 建立可重設測試資料 → 驗證成功 → 勾環境步驟
```

## Bad Example

```text
Scenario Agent 進 Red 後才發現專案連測試指令都沒有，順便重建整個環境
```

# Rule 2 - 一個 Scenario 只建立一位代理

- Level: `MUST`
- 後端或前端每個 `S-n-m` 是一次完整委派單位；建立一位 Scenario Agent，交接 task、e2e、系統分析、API 契約、測試命令與已知進度。
- 該代理在同一脈絡依序執行 Red → Green → Refactor → User Story 層內全綠；不得為三個階段各開一位代理。
- 每一階段仍必須遵守對應 tdd skill；共用脈絡不代表合併 Red、Green、Refactor 的責任。
- 正常執行不得同時平行修改多個 Scenario。若上一次因失敗或工作階段中斷而失去代理脈絡，重試時可建立新代理，但必須交付既有變更、已通過證據與第一個未完成階段，不得假裝仍是原代理。

## Good Example

```text
Scenario Agent A
  S-1-1 Red 合格
  S-1-1 Green 全綠
  S-1-1 Refactor 後仍綠
  US-1 前綴累積測試與契約證據通過
```

## Bad Example

```text
Agent A 寫 Red → 關閉
Agent B 只看摘要做 Green → 關閉
Agent C 重新猜需求做 Refactor
```

# Rule 3 - 整合不走 TDD 三階段

- Level: `MUST`
- `task-integration.md` 的執行單位是 `User Story 完全端對端驗收`，由真實瀏覽器經真實前端、正式 API、後端到可重設資料。
- 進場前後端該 User Story 完成閘門必須已通過；執行時 API Mock 與其他替身必須停用。
- 整合失敗不得製造一個假的 Red：行為缺口回對應層 Scenario 重新跑完整循環；契約不一致以 `api-plan.md` 判定漂移方；接線或環境缺口在整合層補回歸測試後修復。

## Good Example

```text
US-1 前後端閘門已綠 → 停用 Mock → 真實瀏覽器完整驗收
```

## Bad Example

```text
整合先寫一個必紅案例，再用 /tdd-e2e-green 一次修改前後端
```

# Rule 4 - 執行順序跟 task 文件

- Level: `MUST`
- 單一層從第一個未完成步驟往下做；一個 Scenario 完整結束後才進下一個。
- 多層依進場選定順序執行；未通過前置或故事閘門時不得跳到整合。

## Good Example

```text
環境建立 → S-1-1 完整循環 → S-1-2 完整循環 → US-1 完成閘門
```

## Bad Example

```text
先把 US-1 所有 Red 寫完，再批次做所有 Green
```
