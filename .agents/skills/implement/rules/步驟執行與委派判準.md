# Rule 1 - 無 skill 引用的步驟親自執行

- Level: `MUST`
- `task-*.md` 中未標示 `/tdd-e2e-red`／`/tdd-e2e-green`／`/tdd-e2e-refactor` 的 checkbox 步驟（例如 §1 規格閱讀、§2 環境建立、驗證指令），必須由 `/implement` 親自執行。
- 不可把這類步驟丟給 tdd skill，也不可只口頭說「已完成」卻未實際執行。

## Good Example

- 這個例子是好的，因為環境步驟由 implement 落地。

```text
- [ ] 建立 backend/ 骨架 → implement 執行 mkdir／驗證
```

## Bad Example

- 這個例子是壞的，因為把環境建立塞進 `/tdd-e2e-red`。

```text
呼叫 red 時順便請它 npm init
```

# Rule 2 - 標有 tdd skill 的步驟必須委派並帶齊參數

- Level: `MUST`
- 步驟文字含 `/tdd-e2e-red` 且為 **Scenario 格**（`S-n-m`）時：不要一格一呼叫。改為收斂**同一 US** 內所有尚未勾選的 Scenario 級 Red 格（不含「執行本 User Story 的測試…皆為紅燈」驗紅項），一次委派 `/tdd-e2e-red`，並傳：`layer`、`plan-package`、單一 `US` 識別、Scenario 清單（各含 ID／標題與受測行為）。
- 含 `/tdd-e2e-green` 時委派該 skill，並傳：`layer`、`plan-package`、單一 Scenario ID／標題、該格實作計畫（對齊 Red 的 e2e 案例粒度；一次一格一支 Scenario）。
- 含 `/tdd-e2e-refactor` 時委派該 skill，並傳：`layer`、`plan-package`、單一 US 識別、該格實作計畫。
- 該 US 的 Red **驗紅項**（「執行本 User Story 的測試…皆為紅燈」）由 implement 在該 US Scenario Red 批次成功後親自跑該層全套測試確認皆紅，再勾選；不可把驗紅項塞進 red 的 Scenario 清單。
- 缺參數不得委派；應停止並回報。

## Good Example

- 這個例子是好的，因為 Red 一次帶整 US 清單；Green 仍一 Scenario。

```text
DELEGATE /tdd-e2e-red
layer=backend
plan-package=002-meeting-room-booking
US=US-1
Scenarios=[S-1-1…S-1-7 + 各受測行為]

DELEGATE /tdd-e2e-green
layer=backend
plan-package=002-meeting-room-booking
Scenario=S-1-1 …
實作計畫=（該格巢狀條列）
```

## Bad Example

- 這個例子是壞的，因為 Red 仍一格一呼叫，或 green 一次塞整包 US。

```text
DELEGATE /tdd-e2e-red（僅 S-1-1）
DELEGATE /tdd-e2e-red（僅 S-1-2）
…
DELEGATE /tdd-e2e-green US=US-1（無 Scenario）
```

# Rule 3 - 執行順序跟 task 文件，不跳著做

- Level: `MUST`
- 單一層內從第一個未勾選 checkbox 往下依序執行；完成一個再下一個。
- 遇到某 US 的第一個未勾 Scenario Red 時，應一次收斂該 US 剩餘未勾 Scenario Red 做批次委派（見 Rule 2），成功後依回報勾選對應多格，再處理驗紅項與後續 Green。
- 多層時依進場選定順序，完成當層可執行範圍後再進下一層。
- 不可為求快而跳過未勾的 §1／§2 直接做 §3（除非該項已勾選）。

## Good Example

- 這個例子是好的，因為先做未勾的環境項，再對 US-1 批次 Red。

```text
未勾: §2.1 → 先做完並勾選 → 再批次委派 US-1 全部未勾 S-* Red
```

## Bad Example

- 這個例子是壞的，因為 §2 未做完就呼叫一排 Red，或 Red 仍逐格拆呼叫。

```text
環境未勾 → 直接委派 S-1-1…S-1-5（且分成五次呼叫）
```
