# Rule 1 - 成功步驟必須勾選對應 checkbox

- Level: `MUST`
- 每一步親自執行或委派成功後，必須把該步在對應 `task-*.md` 的 `- [ ]` 改為 `- [x]`（或 `- [X]`）。
- 若 `/tdd-e2e-red` **US 批次**回報列出多支已完成 Scenario：必須把回報中**每一支**對應 Scenario checkbox 皆勾選；驗紅項另於親自跑測確認後勾選。
- 若批次中途失敗：只勾選回報中已合格紅的 Scenario；卡關當支與後續未做項保持未勾。
- 不可只在對話說完成卻不改檔；續跑以未勾項為準。

## Good Example

- 這個例子是好的，因為檔案進度與批次回報一致。

```md
Red 批次 done: S-1-1, S-1-2
→ task 中兩格皆 [x]；S-1-3 仍 [ ]
```

## Bad Example

- 這個例子是壞的，因為對話稱完成但 checkbox 仍空，或批次成功只勾第一格。

```md
- [ ] `/tdd-e2e-red` — S-1-1 …
（對話：US-1 Red 批次好了）
```

# Rule 2 - 失敗立即停止，已勾保留

- Level: `MUST`
- 任一步驟失敗（含委派 skill 回報失敗／環境洞／非預期結果）：立即停止後續步驟。
- 已成功並勾選的項目保持已勾；失敗當步不勾選。
- 必須回報卡點與建議下一步，等待使用者再決定如何續跑；不可自動跳過失敗格。

## Good Example

- 這個例子是好的，因為停在失敗格且保留進度。

```text
已勾: §1、§2、S-1-1 Red
失敗: S-1-2 Red（環境洞）→ 停止，不跑後面
```

## Bad Example

- 這個例子是壞的，因為失敗後自動跳過繼續 Green。

```text
S-1-2 Red 失敗 → 跳過並開始 Green
```

# Rule 3 - 子 skill 不代勾；勾選是 implement 的職責

- Level: `MUST`
- `/tdd-e2e-red`／`green`／`refactor` 回報成功後，由 `/implement` 負責勾選；不可期待子 skill 改 task 檔。

## Good Example

- 這個例子是好的，因為委派成功後 implement 寫回 checkbox。

```text
red 回報成功 → implement 勾該格
```

## Bad Example

- 這個例子是壞的，因為假定 red 會自己勾 task。

```text
等 red 去改 task-backend.md
```
